    🎯 Conceptual Overview & Derivation

    The Fragility of Ad-Hoc Scripts and the Imperative of Workflow Orchestration

    In computational science and machine learning data engineering, the default method of analysis has historically relied on informal scripts: linear shell scripts (run_all.sh), manual Jupyter notebooks, or ad-hoc Python glue code (Peng, 2011; Boettiger, 2015). While accessible for exploratory prototyping, unorchestrated scripts represent a catastrophic failure mode in production systems (Stodden et al., 2016): 1. Implicit Environmental Assumptions: Scripts assume the host machine has specific dynamically linked C libraries, NVIDIA driver minor versions, and locale environment variables. 2. Lack of Idempotent Caching: A pipeline that crashes at step 9 out of 10 forces engineers to either manually retrace intermediate outputs or redundantly recompute hours of expensive upstream transformations. 3. Implicit Dependency Graphs: Execution order is coupled to serial command execution rather than dataflow causality, making distributed cloud and high-performance computing (HPC) parallelization error-prone and brittle (Di Tommaso et al., 2017; Köster & Rahmann, 2012).

    Scientific workflow orchestrators—principally Nextflow, Snakemake, and the Common Workflow Language (CWL)—elevate computational pipelines from imperative scripts to declarative, directed acyclic graphs (DAGs). Coupled with immutable Open Container Initiative (OCI) containers (Docker, Singularity, Apptainer), modern workflow management guarantees that execution logic, resource allocations, and binary runtimes are fully decoupled from underlying physical infrastructure (Amstutz et al., 2016; Nüst et al., 2020).

    +---------------------------------------------------------------------------------------------------+
|                        THE WORKFLOW AND RUNTIME REPRODUCIBILITY SPECTRUM                          |
+---------------------------------------------------------------------------------------------------+
| LEVEL 0: Imperative Script   | LEVEL 1: Virtualenv / Conda | LEVEL 2: Containerized OCI    | LEVEL 3: Declarative W-DAG    |
| - Unversioned bash / ipynb   | - Pinned Python packages    | - Pinned Docker / Apptainer   | - Nextflow / Snakemake / CWL  |
| - Host libc / driver drift   | - Host OS & C-libs drift    | - Immutable OS rootfs Merkle  | - Content-addressed memoize   |
| - Zero caching / restart     | - Manual serial execution   | - Zero host libc drift        | - Critical path parallelized  |
| - Delta_env >> 0 (Failure)   | - Non-deterministic state   | - Delta_env == 0              | - H(Y | X, I, Pipe) = 0       |
+---------------------------------------------------------------------------------------------------+

    Mathematical Formulations of Workflow DAGs and Container Invariants

    To formalize scientific workflows mathematically, we formulate four foundational definitions governing execution DAG scheduling, content-addressed memoization, container overlayfs layer algebras, and declarative determinism invariants.

    Definition 13.7.1: Workflow Execution Directed Acyclic Graph (W-DAG) & Topological Scheduling

    A scientific computational workflow is formally modeled as a directed, edge-weighted acyclic multigraph:

    \[\mathcal{W} = \left( \mathcal{T}_{\text{tasks}}, \mathcal{D}_{\text{edges}}, \mathbf{c}, \mathbf{w} \right)\]

    where: - \(\mathcal{T}_{\text{tasks}} = \{t_1, t_2, \dots, t_N\}\) denotes the set of atomic computational tasks (processes or rules). - \(\mathcal{D}_{\text{edges}} \subset \mathcal{T}_{\text{tasks}} \times \mathcal{T}_{\text{tasks}}\) denotes causal dataflow dependencies (channels, pipes, or materialized intermediate files). A directed edge \((u, v) \in \mathcal{D}_{\text{edges}}\) indicates that task \(v\) strictly consumes one or more output files generated by task \(u\). - \(\mathbf{c}(t) \in \mathbb{R}_+^d\) represents the vector of hardware resource requirements for task \(t\) (e.g., number of CPU cores, GPU count, memory in gigabytes). - \(\mathbf{w}(t) \in \mathbb{R}_+\) denotes the deterministic execution wall-clock duration of task \(t\).

    A valid workflow execution schedule is a mapping \(\sigma: \mathcal{T}_{\text{tasks}} \to \mathbb{R}_+\) assigning each task a start time \(\sigma(t) \ge 0\) satisfying the Causal Precedence Invariant:

    \[\forall (u, v) \in \mathcal{D}_{\text{edges}}: \quad \sigma(v) \ge \sigma(u) + \mathbf{w}(u) + \delta_{\text{io}}(u, v)\]

    where \(\delta_{\text{io}}(u, v) \ge 0\) represents the network or filesystem I/O latency required to transfer intermediate data from task \(u\) to task \(v\).

    The Critical Path & Makespan Lower Bound:

    Let \(\text{Paths}(\mathcal{W})\) be the set of all directed paths from source tasks (\(\text{in-degree} = 0\)) to sink tasks (\(\text{out-degree} = 0\)). The Critical Path Length \(\mathcal{C}^*(\mathcal{W})\) represents the theoretical lower bound on execution makespan under infinite parallel computing resources:

    \[\mathcal{C}^*(\mathcal{W}) = \max_{\pi \in \text{Paths}(\mathcal{W})} \sum_{t \in \pi} \left( \mathbf{w}(t) + \sum_{(u, v) \in \text{Edges}(\pi)} \delta_{\text{io}}(u, v) \right)\]

    Any task \(t\) lying on the critical path has zero scheduling slack: a delay in \(t\) delays the entire scientific pipeline (Köster & Rahmann, 2012; Di Tommaso et al., 2017).

    Definition 13.7.2: Content-Addressed Task Memoization & Cache Invalidation Invariant

    To guarantee idempotent re-execution and eliminate redundant compute, modern workflow engines employ Content-Addressed Task Memoization.

    For any task \(t \in \mathcal{T}_{\text{tasks}}\), the engine computes a composite cryptographic Execution Cache Key \(\mathcal{K}(t)\):

    \[\mathcal{K}(t) = \text{SHA256}\left( \mathcal{H}_{\text{code}}(t) \parallel \mathcal{H}_{\text{env}}(t) \parallel \text{sort}\left( \left\{ \mathcal{H}_{\text{data}}(i) \;\middle|\; i \in \text{Inputs}(t) \right\} \right) \parallel \text{Serialize}(\text{Params}(t)) \right)\]

    where: - \(\mathcal{H}_{\text{code}}(t)\) is the cryptographic hash of the executable command script or binary code. - \(\mathcal{H}_{\text{env}}(t)\) is the immutable digest of the container image (e.g., docker-pullable://quay.io/biocontainers/samtools@sha256:...). - \(\mathcal{H}_{\text{data}}(i)\) represents the content-addressed SHA-256 digest of input file \(i\). - \(\text{Params}(t)\) represents serialized runtime arguments (e.g., learning rate, alignment thresholds).

    Theorem 13.7.1 (Idempotent Memoization Invariant):

    Assume task \(t\) executes a deterministic transformation \(f_t: \text{Inputs} \times \text{Params} \to \text{Outputs}\). If \(\mathcal{K}(t_1) = \mathcal{K}(t_2)\), then:

    \[f_{t_1}(\text{Inputs}_1, \text{Params}_1) \equiv f_{t_2}(\text{Inputs}_2, \text{Params}_2) \quad \text{with probability } 1 - 2^{-256}\]

    If \(\mathcal{K}(t)\) matches an entry in the persistent cache database, the workflow engine completely bypasses task execution, materializing the cached output files into the working directory via zero-copy filesystem hard links or symlinks in \(\mathcal{O}(1)\) time (Di Tommaso et al., 2017).

    Cache Invalidation Avalanche:

    If an upstream input file \(i_0\) is perturbed by a single byte: $\(\Delta \text{Payload}(i_0) \neq 0 \implies \mathcal{K}(t_{\text{upstream}})' \neq \mathcal{K}(t_{\text{upstream}})\)$ This invalidates the cache key for task \(t_{\text{upstream}}\) and cascades downstream across its reachability cone \(\mathcal{B}_{\text{down}}(t_{\text{upstream}})\), triggering recomputation only for affected nodes while all independent parallel tasks hit the cache with zero compute latency (Köster & Rahmann, 2012).

    Definition 13.7.3: OCI Container Layering & Merkle State Transition Algebra

    An Open Container Initiative (OCI) image \(\mathcal{I}\) is formalized as an immutable stack of content-addressed filesystem layers composed via the union overlay operator \(\oplus\):

    \[\mathcal{I} = L_0 \oplus L_1 \oplus \dots \oplus L_k\]

    where each layer \(L_j = (\Delta \mathcal{F}_j, \mathcal{H}_j)\) represents a tarball changeset \(\Delta \mathcal{F}_j\) over the parent layer filesystem, addressed by cryptographic digest \(\mathcal{H}_j = \text{SHA256}(\Delta \mathcal{F}_j)\).

    We define the Runtime Environment Drift Metric \(\Delta_{\text{env}}(\mathcal{E}_{\text{host}}, \mathcal{E}_{\text{target}})\) between host system \(\mathcal{E}_{\text{host}}\) and target execution environment \(\mathcal{E}_{\text{target}}\) as the Hamming distance across the set of dynamically linked shared library application binary interfaces (ABIs):

    \[\Delta_{\text{env}}\left( \mathcal{E}_{\text{host}}, \mathcal{E}_{\text{target}} \right) = \sum_{lib \in \mathcal{S}_{\text{libs}}} \mathbb{I}\left( \text{SONAME}(lib) \text{ or } \text{SymbolDigest}(lib) \text{ differs} \right)\]
    Theorem 13.7.2 (Zero-Drift Container Invariant):

    While executing uncontainerized scientific code directly on bare-metal host operating systems yields non-zero drift \(\Delta_{\text{env}} > 0\) due to host package variations (such as GNU libc floating-point math differences across OS distributions), executing inside a pinned OCI container image \(\mathcal{I}_{\text{pinned}}\) enforces:

    \[\Delta_{\text{env}}\left( \mathcal{E}_{\text{container}}, \mathcal{I}_{\text{pinned}} \right) \equiv 0\]

    eliminating compiler ABI mismatch, Python interpreter minor-version divergence, and operating system library drift (Boettiger, 2015; Nüst et al., 2020).

    Definition 13.7.4: Common Workflow Language (CWL) Declarative Execution Invariant

    Let a declarative scientific workflow be specified in CWL or Nextflow DSL2.

    The workflow engine defines a formal evaluation operator \(\Phi_{\text{CWL}}\) mapping typed inputs \(\mathcal{X}_{\text{in}}\), pinned container environment \(\mathcal{I}\), and pipeline specification \(\mathcal{P}_{\text{pipeline}}\) to terminal outputs \(\mathcal{Y}_{\text{out}}\):

    \[\Phi_{\text{CWL}}: \mathcal{X}_{\text{in}} \times \mathcal{I} \times \mathcal{P}_{\text{pipeline}} \longrightarrow \mathcal{Y}_{\text{out}}\]

    The core requirement of scientific workflow engineering is the Declarative Determinism Invariant:

    \[H\left( \mathcal{Y}_{\text{out}} \;\middle|\; \mathcal{X}_{\text{in}}, \mathcal{I}, \mathcal{P}_{\text{pipeline}} \right) = 0\]

    such that the conditional information entropy of output datasets given the input manifest, container digest, and workflow definition is identically zero.

    Under this invariant, execution across heterogeneous computing platforms—whether a local MacBook laptop, an on-premise SLURM high-performance computing cluster, Amazon Web Services (AWS Batch), or Google Cloud Life Sciences—produces bitwise identical scientific datasets without requiring code modifications (Amstutz et al., 2016; Di Tommaso et al., 2017).

    💻 Runnable Executable Python Implementation

    The following production-grade implementation, ReproducibleWorkflowOrchestrator, provides complete mathematical validation for workflow execution DAGs, topological scheduling, and content-addressed memoization. It implements: 1. Pydantic V2 data structures for workflow tasks, dataflow channels, OCI container images, and task cache records. 2. Kahn's topological sort algorithm, strictly detecting and rejecting cyclic dependency graphs. 3. Critical Path calculation (\(\mathcal{C}^*\)) identifying the makespan lower bound under infinite compute parallelism. 4. Content-addressed task memoization (\(\mathcal{K}(t)\)) executing zero-copy cache restoration on identical runs.

    """
ReproducibleWorkflowOrchestrator: Production-grade validation and mathematical auditing
for workflow DAG scheduling, critical path makespan bounds, content-addressed task memoization,
and OCI container runtime isolation.
"""

from __future__ import annotations
import math
import hashlib
from typing import Dict, List, Optional, Set, Tuple, Any
from enum import Enum
from pydantic import BaseModel, Field, field_validator, model_validator


class TaskExecutionStatus(str, Enum):
    PENDING = "PENDING"
    CACHED = "CACHED"
    RUNNING = "RUNNING"
    COMPLETED = "COMPLETED"
    FAILED = "FAILED"


class WorkflowTask(BaseModel):
    task_id: str = Field(..., min_length=1)
    script_command: str = Field(..., min_length=1)
    container_image_digest: str = Field(..., min_length=8, description="OCI image digest, e.g. sha256:...")
    duration_seconds: float = Field(..., gt=0.0, description="Task execution wall-clock time w(t)")
    required_cpus: int = Field(default=1, ge=1)
    required_memory_gb: float = Field(default=2.0, ge=0.5)
    parameters: Dict[str, Any] = Field(default_factory=dict)
    input_file_hashes: Dict[str, str] = Field(default_factory=dict, description="Filename -> SHA-256")


class WorkflowDependency(BaseModel):
    upstream_task_id: str
    downstream_task_id: str
    transfer_latency_seconds: float = Field(default=0.0, ge=0.0, description="I/O channel latency delta_io")


class TaskCacheRecord(BaseModel):
    cache_key: str
    task_id: str
    output_hashes: Dict[str, str]
    created_timestamp: str


class WorkflowExecutionReport(BaseModel):
    workflow_name: str
    task_count: int
    topological_order: List[str]
    critical_path_tasks: List[str]
    critical_path_makespan_seconds: float
    total_serial_work_seconds: float
    theoretical_parallel_speedup: float
    executed_tasks_count: int
    cached_tasks_count: int
    execution_status: TaskExecutionStatus


class ReproducibleWorkflowOrchestrator:
    """
    Mathematical engine implementing Definitions 13.7.1 through 13.7.4.
    """

    def __init__(self, workflow_name: str = "GenomicsPipeline"):
        self.workflow_name = workflow_name
        self.tasks: Dict[str, WorkflowTask] = {}
        self.dependencies: List[WorkflowDependency] = []
        self.cache_database: Dict[str, TaskCacheRecord] = {}

    def add_task(self, task: WorkflowTask) -> None:
        if task.task_id in self.tasks:
            raise ValueError(f"Task '{task.task_id}' already registered.")
        self.tasks[task.task_id] = task

    def add_dependency(self, dep: WorkflowDependency) -> None:
        if dep.upstream_task_id not in self.tasks or dep.downstream_task_id not in self.tasks:
            raise KeyError(f"Endpoints ({dep.upstream_task_id} -> {dep.downstream_task_id}) must exist in tasks.")
        self.dependencies.append(dep)

    def compute_task_cache_key(self, task: WorkflowTask) -> str:
        """
        Computes the composite content-addressed cache key K(t) under Definition 13.7.2:
        K(t) = SHA256( H_code || H_env || sort(H_inputs) || Params )
        """
        h_code = hashlib.sha256(task.script_command.encode("utf-8")).hexdigest()
        h_env = task.container_image_digest

        # Sorted input file digests
        sorted_inputs = sorted([f"{k}:{v}" for k, v in task.input_file_hashes.items()])
        h_inputs = hashlib.sha256(";".join(sorted_inputs).encode("utf-8")).hexdigest()

        # Serialized parameters
        sorted_params = sorted([f"{k}:{v}" for k, v in task.parameters.items()])
        h_params = hashlib.sha256(";".join(sorted_params).encode("utf-8")).hexdigest()

        block = f"{h_code}|{h_env}|{h_inputs}|{h_params}"
        cache_key = hashlib.sha256(block.encode("utf-8")).hexdigest()
        return cache_key

    def compute_topological_schedule(self) -> List[str]:
        """
        Executes Kahn's algorithm to compute a valid topological ordering of tasks.
        Raises ValueError if a cycle is detected.
        """
        in_degree: Dict[str, int] = {t: 0 for t in self.tasks}
        adj_list: Dict[str, List[str]] = {t: [] for t in self.tasks}

        for dep in self.dependencies:
            adj_list[dep.upstream_task_id].append(dep.downstream_task_id)
            in_degree[dep.downstream_task_id] += 1

        queue = [t for t, deg in in_degree.items() if deg == 0]
        topo_order: List[str] = []

        while queue:
            curr = queue.pop(0)
            topo_order.append(curr)

            for neighbor in adj_list[curr]:
                in_degree[neighbor] -= 1
                if in_degree[neighbor] == 0:
                    queue.append(neighbor)

        if len(topo_order) != len(self.tasks):
            raise ValueError("Workflow graph contains cyclic dependencies! Violates DAG invariant.")

        return topo_order

    def compute_critical_path(self) -> Tuple[List[str], float]:
        """
        Calculates the Critical Path Length C*(W) using dynamic programming on DAG topological order.
        """
        topo_order = self.compute_topological_schedule()

        # earlist_finish[t] represents longest path from any source to end of t
        earliest_finish: Dict[str, float] = {t: self.tasks[t].duration_seconds for t in self.tasks}
        predecessor: Dict[str, Optional[str]] = {t: None for t in self.tasks}

        # Build incoming edges lookup
        incoming: Dict[str, List[WorkflowDependency]] = {t: [] for t in self.tasks}
        for dep in self.dependencies:
            incoming[dep.downstream_task_id].append(dep)

        for t in topo_order:
            for dep in incoming[t]:
                u = dep.upstream_task_id
                finish_via_u = earliest_finish[u] + dep.transfer_latency_seconds + self.tasks[t].duration_seconds
                if finish_via_u > earliest_finish[t]:
                    earliest_finish[t] = finish_via_u
                    predecessor[t] = u

        # Find sink task with maximum finish time
        sink_task = max(earliest_finish.keys(), key=lambda k: earliest_finish[k])
        critical_makespan = earliest_finish[sink_task]

        # Reconstruct critical path
        path: List[str] = []
        curr: Optional[str] = sink_task
        while curr is not None:
            path.append(curr)
            curr = predecessor[curr]
        path.reverse()

        return path, critical_makespan

    def execute_workflow(self) -> WorkflowExecutionReport:
        """
        Simulates workflow execution with content-addressed task memoization.
        """
        topo_order = self.compute_topological_schedule()
        crit_path, makespan = self.compute_critical_path()

        total_serial_work = sum(t.duration_seconds for t in self.tasks.values())
        speedup = total_serial_work / makespan if makespan > 0 else 1.0

        executed_count = 0
        cached_count = 0

        for t_id in topo_order:
            task = self.tasks[t_id]
            key = self.compute_task_cache_key(task)

            if key in self.cache_database:
                # Cache hit: zero compute time
                cached_count += 1
            else:
                # Cache miss: execute task and store outputs
                executed_count += 1
                mock_output_hash = hashlib.sha256(f"out_{task.task_id}".encode("utf-8")).hexdigest()
                self.cache_database[key] = TaskCacheRecord(
                    cache_key=key,
                    task_id=task.task_id,
                    output_hashes={"output.tsv": mock_output_hash},
                    created_timestamp="2026-11-13T08:50:00Z",
                )

        return WorkflowExecutionReport(
            workflow_name=self.workflow_name,
            task_count=len(self.tasks),
            topological_order=topo_order,
            critical_path_tasks=crit_path,
            critical_path_makespan_seconds=makespan,
            total_serial_work_seconds=total_serial_work,
            theoretical_parallel_speedup=speedup,
            executed_tasks_count=executed_count,
            cached_tasks_count=cached_count,
            execution_status=TaskExecutionStatus.COMPLETED,
        )

    Exercise 1: Computing the Critical Path Makespan and Parallel Speedup of a Genomics Workflow DAG

    A genomics data processing pipeline consists of 6 tasks with the following wall-clock execution durations and dataflow dependencies: - \(t_1\) (Quality Control): \(\mathbf{w}(t_1) = 60\text{s}\), no inputs. - \(t_2\) (Read Trimming): \(\mathbf{w}(t_2) = 120\text{s}\), depends on \(t_1\). - \(t_3\) (Reference Genome Indexing): \(\mathbf{w}(t_3) = 180\text{s}\), no inputs. - \(t_4\) (Sequence Alignment): \(\mathbf{w}(t_4) = 480\text{s}\), depends on \(t_2\) and \(t_3\). - \(t_5\) (Variant Calling): \(\mathbf{w}(t_5) = 360\text{s}\), depends on \(t_4\). - \(t_6\) (Annotation): \(\mathbf{w}(t_6) = 120\text{s}\), depends on \(t_5\).

    Assume I/O transfer latency is negligible (\(\delta_{\text{io}} = 0\)).

    1. Identify all valid directed paths from sources to sinks in the workflow DAG \(\mathcal{W}\).
    2. Calculate the Critical Path Length \(\mathcal{C}^*(\mathcal{W})\) and identify the bottleneck tasks.
    3. Compute the Total Serial Work \(\mathcal{W}_{\text{serial}}\) and the Maximum Theoretical Parallel Speedup \(S_{\infty} = \frac{\mathcal{W}_{\text{serial}}}{\mathcal{C}^*(\mathcal{W})}\).
    Reveal Complete Step-by-Step Solution

    Step 1: Identifying Valid Source-to-Sink Directed Paths

    The source tasks (in-degree 0) are \(t_1\) and \(t_3\). The only sink task (out-degree 0) is \(t_6\).

    The directed dependencies are: - \(t_1 \to t_2 \to t_4 \to t_5 \to t_6\) - \(t_3 \to t_4 \to t_5 \to t_6\)

    This yields exactly two directed paths from source to sink: - Path 1: \(\pi_1 = (t_1, t_2, t_4, t_5, t_6)\) - Path 2: \(\pi_2 = (t_3, t_4, t_5, t_6)\)

    Step 2: Calculating Critical Path Length \(\mathcal{C}^*(\mathcal{W})\)

    We evaluate the cumulative duration along each path:

    \[\text{Length}(\pi_1) = \mathbf{w}(t_1) + \mathbf{w}(t_2) + \mathbf{w}(t_4) + \mathbf{w}(t_5) + \mathbf{w}(t_6) = 60 + 120 + 480 + 360 + 120 = 1,140\text{ seconds}\]
    \[\text{Length}(\pi_2) = \mathbf{w}(t_3) + \mathbf{w}(t_4) + \mathbf{w}(t_5) + \mathbf{w}(t_6) = 180 + 480 + 360 + 120 = 1,140\text{ seconds}\]

    Both paths have an identical length of 1,140 seconds (19.0 minutes).

    Therefore, the Critical Path Length is:

    \[\mathcal{C}^*(\mathcal{W}) = 1,140\text{ seconds}\]

    The critical path tasks encompass all tasks in the pipeline. Note that while \(t_1 \to t_2\) takes 60s + 120s = 180s, task \(t_3\) also takes 180s, meaning both branches arrive at task \(t_4\) at the exact same moment.

    Step 3: Calculating Total Serial Work and Parallel Speedup

    Total serial work is the sum of all task durations:

    \[\mathcal{W}_{\text{serial}} = \sum_{i=1}^6 \mathbf{w}(t_i) = 60 + 120 + 180 + 480 + 360 + 120 = 1,320\text{ seconds} \quad (22.0\text{ minutes})\]

    The theoretical maximum parallel speedup under infinite compute resources (\(S_{\infty}\)) is:

    \[S_{\infty} = \frac{\mathcal{W}_{\text{serial}}}{\mathcal{C}^*(\mathcal{W})} = \frac{1,320}{1,140} \approx 1.1579 \approx 1.16\]

    Even with an infinite number of parallel worker cores, the maximum speedup is 1.16x because sequence alignment (\(t_4\)) and variant calling (\(t_5\)) are strictly serial bottlenecks that consume over 71% of total pipeline work.

    Step 1: Hyperparameter Perturbation in Task 4

    Under Definition 13.7.2, the cache key is computed as:

    \[\mathcal{K}(t) = \text{SHA256}\left( \mathcal{H}_{\text{code}} \parallel \mathcal{H}_{\text{env}} \parallel \text{sort}(\mathcal{H}_{\text{inputs}}) \parallel \text{Params} \right)\]
    • Tasks 1, 2, and 3: None of their code, container digests, input files, or parameters were altered. Therefore: \(\mathcal{K}(t_1)' = \mathcal{K}(t_1), \quad \mathcal{K}(t_2)' = \mathcal{K}(t_2), \quad \mathcal{K}(t_3)' = \mathcal{K}(t_3)\). All three tasks produce identical cache keys, hitting the persistent cache database. Execution is bypassed in \(\mathcal{O}(1)\) time.
    • Task 4: The parameter string changed: \(\text{Params}(t_4)' \neq \text{Params}(t_4) \implies \mathcal{K}(t_4)' \neq \mathcal{K}(t_4)\). Task 4 suffers a cache miss and is the only task re-executed. Compute savings: over 90% of total pipeline time is preserved.

    Step 2: Container Image Digest Perturbation in Task 2

    When the container image digest for Task 2 is modified from v1 to v2: 1. Task 1: Unaffected. \(\mathcal{K}(t_1)' = \mathcal{K}(t_1) \implies\) Cache Hit (bypassed). 2. Task 2: The environment digest changed: \(\mathcal{H}_{\text{env}}(t_2)' \neq \mathcal{H}_{\text{env}}(t_2) \implies \mathcal{K}(t_2)' \neq \mathcal{K}(t_2)\). Task 2 suffers a cache miss and must be re-executed inside the new container. 3. Task 3: Task 3 consumes the output files generated by Task 2. Because Task 2 re-ran, the output file digests change: \(\mathcal{H}_{\text{inputs}}(t_3)' \neq \mathcal{H}_{\text{inputs}}(t_3) \implies \mathcal{K}(t_3)' \neq \mathcal{K}(t_3)\). Task 3 suffers a downstream cache invalidation and must be re-executed. 4. Task 4: Consumes the output of Task 3: \(\mathcal{H}_{\text{inputs}}(t_4)' \neq \mathcal{H}_{\text{inputs}}(t_4) \implies \mathcal{K}(t_4)' \neq \mathcal{K}(t_4)\). Task 4 suffers a downstream cache invalidation and must be re-executed.
