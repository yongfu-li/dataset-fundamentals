    🎯 Conceptual Overview & Theoretical Foundations

    The historical boundary separating structured relational data warehouses, unstructured cloud object data lakes, and specialized AI similarity engines has dissolved into unified Data Intelligence Platforms and Multimodal Data Lakehouses (Armbrust et al., 2020; Zaharia et al., 2021; Nambiar & Mundra, 2022). Rather than duplicating terabytes of raw assets across incompatible database silos, contemporary architectures execute analytical SQL queries, distributed tensor shuffling, and sub-millisecond vector retrieval directly against open columnar files in cloud object storage.

    Four core technological innovations anchor modern scalable data management: 1. ACID Transactions & Optimistic Concurrency Control (OCC): Enforcing serializable snapshot isolation and deterministic time-travel directly over immutable cloud object storage (Armbrust et al., 2020). 2. Billion-Scale Approximate Nearest Neighbor (ANN) Vector Search: Traversing billion-vector embedding manifolds in logarithmic time via Hierarchical Navigable Small World (HNSW) graphs (Malkov & Yashunin, 2018) compressed \(32\times - 64\times\) via Product Quantization (Jégou et al., 2011; Johnson et al., 2021). 3. Random-Access Multimodal Storage Formats: Overcoming batch-analytical Parquet constraints with random-access AI columnar formats like Apache Lance. 4. Decentralized Data Mesh & Stateful Stream Checkpointing: Pairing domain-owned data product contracts (Dehghani, 2022) with asynchronous continuous stateful execution (Carbone et al., 2017).

    Definition 12.10.1: Lakehouse Optimistic Concurrency Control (OCC) Validation

    Cloud object stores (such as AWS S3 and GCS) lack native multi-file ACID locking primitives. Open table formats (Delta Lake, Apache Iceberg) achieve serializable snapshot isolation over immutable object files using Optimistic Concurrency Control (OCC) governed by an atomic append-only transaction log (Armbrust et al., 2020; Zaharia et al., 2021).

    A distributed transaction \(T_i\) proceeds through three sequential phases: 1. Read Phase: \(T_i\) reads snapshot version \(V_{\text{start}}\), recording the set of input Parquet files \(\mathcal{R}(T_i)\) scanned. 2. Execution Phase: \(T_i\) writes newly generated Parquet files \(\mathcal{W}(T_i)\) and marks obsolete files \(\mathcal{D}(T_i)\) privately without mutating the active catalog. 3. Validate & Commit Phase: Before atomically writing commit entry \(V_{\text{commit}} + 1\), \(T_i\) inspects all transactions concurrently committed in the interval \([V_{\text{start}} + 1, V_{\text{commit}}]\).

    The commit succeeds if and only if the OCC Validation Predicate holds:

    \[ \begin{aligned} \text{Validate}(T_i) = \Bigg[ &\Big( \mathcal{R}(T_i) \cup \mathcal{W}(T_i) \cup \mathcal{D}(T_i) \Big) \\ &\cap \left( \bigcup_{V = V_{\text{start}} + 1}^{V_{\text{commit}}} \Big( \mathcal{W}_{\text{committed}}(V) \cup \mathcal{D}_{\text{committed}}(V) \Big) \right) = \emptyset \Bigg] \end{aligned} \]

    If the intersection is non-empty, another worker concurrently modified or deleted a file that \(T_i\) depends on; \(T_i\) aborts immediately to preserve serializability and restarts cleanly against the new snapshot \(V_{\text{commit}}\).

    Definition 12.10.2: Immutable Log Time-Travel Reconstruction (\(\mathcal{D}(t)\))

    Because every Lakehouse transaction appends immutable \(\text{Add}(f)\) and \(\text{Remove}(f)\) metadata records rather than overwriting active tables in place, historical dataset states remain mathematically deterministic across time.

    Let \(\mathcal{F}\) represent the universal set of physical files ever written to the table path. A Time-Travel Query targeting historical timestamp or snapshot index \(t\) reconstructs the exact bitwise file manifest \(\mathcal{D}(t)\) via:

    \[ \begin{aligned} \mathcal{D}(t) = \Big\{ f \in \mathcal{F} \;\Big|\; &\text{commit}(\text{Add}(f)) \le t \;\land \\ &\Big( \text{commit}(\text{Remove}(f)) > t \;\lor\; \text{Remove}(f) = \emptyset \Big) \Big\} \end{aligned} \]

    Similarly, stateful streaming engines like Apache Flink complement Lakehouse commits using Asynchronous Barrier Snapshotting (a variant of the Chandy-Lamport distributed snapshot algorithm) (Carbone et al., 2017), persisting distributed operator state checkpoints to object storage without halting continuous event ingestion.

    Definition 12.10.3: HNSW Graph Navigation & Exponential Layer Decay

    Given a corpus of \(N\) dense embeddings \(\mathcal{X} = \{\mathbf{x}_1, \dots, \mathbf{x}_N\} \subset \mathbb{R}^d\), exact linear \(k\)-Nearest Neighbor (\(k\)-NN) search evaluates:

    \[ \text{NN}(\mathbf{q}) = \arg\min_{\mathbf{x}_i \in \mathcal{X}} \| \mathbf{q} - \mathbf{x}_i \|_2^2 \]

    requiring \(\mathcal{O}(N \cdot d)\) floating-point operations per query. For \(N = 10^8\) and \(d = 1536\), each query requires \(1.53 \times 10^{11}\) operations—capping throughput below 2 queries/sec.

    Hierarchical Navigable Small World (HNSW) graphs reduce search complexity via a multi-layer hierarchy of proximity graphs (Malkov & Yashunin, 2018). When inserting vector \(\mathbf{x}_i\), its maximum assigned hierarchical layer \(\ell_i\) is drawn from an exponentially decaying probability distribution:

    \[ \ell_i = \left\lfloor -\ln\left( \text{uniform}(0, 1) \right) \cdot m_L \right\rfloor \implies p(\text{layer } \ell) = e^{-\ell / m_L} \]

    where \(m_L\) is the layer normalization factor. Upper layers form sparse, long-range express highways across the vector manifold, while Layer 0 contains all \(N\) vertices with dense local neighborhoods. A search greedily descends from the sparse top entry point to Layer 0, achieving logarithmic search complexity:

    \[ T_{\text{HNSW}} = \mathcal{O}(\log N \cdot d) \]

    Definition 12.10.4: Product Quantization (PQ) Compression & Asymmetric Distance Bounds

    Storing \(N = 10^9\) high-dimensional FP32 vectors (\(d = 768\)) requires \(10^9 \times 768 \times 4\text{ bytes} \approx 3.07\text{ Terabytes}\) of host RAM. Product Quantization (PQ) compresses embeddings into compact byte codes while preserving inner-product geometry (Jégou et al., 2011; Johnson et al., 2021).

    Each vector \(\mathbf{x} \in \mathbb{R}^d\) is partitioned into \(M\) orthogonal sub-vectors of reduced dimension \(d^* = d / M\):

    \[ \mathbf{x} = \left[ \mathbf{u}_1 \mathbin{\Vert} \mathbf{u}_2 \mathbin{\Vert} \dots \mathbin{\Vert} \mathbf{u}_M \right], \quad \mathbf{u}_m \in \mathbb{R}^{d^*} \]

    Within each subspace \(m \in \{1, \dots, M\}\), \(k\)-means clustering learns a codebook \(\mathcal{Q}_m = \{\mathbf{q}_{m,1}, \dots, \mathbf{q}_{m,K}\}\) of \(K\) centroids (typically \(K = 256 = 2^8\), fitting in 1 byte). Vector \(\mathbf{x}\) is encoded as an \(M\)-byte integer tuple:

    \[ \mathbf{c}_x = \left[ \arg\min_{k \in [1, K]} \|\mathbf{u}_1 - \mathbf{q}_{1,k}\|_2, \dots, \arg\min_{k \in [1, K]} \|\mathbf{u}_M - \mathbf{q}_{M,k}\|_2 \right] \]

    Compression Ratio

    Comparing raw 32-bit floating-point storage against \(M\) indices of \(\lceil \log_2 K \rceil = 8\) bits:

    \[ \mathcal{C}_{\text{PQ}} = \frac{d \times 32\text{ bits}}{M \times \lceil \log_2 K \rceil\text{ bits}} = \frac{32 d}{8 M} = \frac{4d}{M} \]

    Asymmetric Distance Computation (ADC)

    At query time, an unquantized query \(\mathbf{y} = [\mathbf{y}_1 \mathbin{\Vert} \dots \mathbin{\Vert} \mathbf{y}_M]\) computes a lookup distance table \(D \in \mathbb{R}^{M \times K}\) once per query in \(\mathcal{O}(d \cdot K)\) operations. Approximate squared Euclidean distance to any compressed database code \(\mathbf{c}_x\) is then evaluated via \(M\) fast array additions:

    \[ \hat{d}(\mathbf{y}, \mathbf{c}_x)^2 = \sum_{m=1}^M \left\| \mathbf{y}_m - \mathbf{q}_{m, c_{x,m}} \right\|_2^2 = \sum_{m=1}^M D[m, c_{x,m}] \]

    For \(d = 768\) and \(M = 96\), PQ yields an exact \(32\times\) memory compression, allowing a 1-billion-vector index (\(3\text{ TB}\)) to fit comfortably in \(96\text{ GB}\) of RAM with \(> 95\%\) recall@10.

    Industrial Best Practice: Multimodal Vector Lakehouses with Apache Lance

    Modern AI pipelines unify structured SQL analytics and vector similarity search directly inside open multimodal formats like Apache Lance (LanceDB). Unlike Apache Parquet, which requires decompressing entire 128 MB row groups for single-row reads, Lance provides \(\mathcal{O}(1)\) random point lookups and native embedded HNSW/IVF-PQ vector indices, accelerating multimodal RAG and PyTorch DataLoader training by up to \(100\times\).

    Common Pitfall / Anti-Pattern: Brute-Force Vector Scan Collapse

    Running exact brute-force cosine similarity across 100 million 1536-dimensional embeddings consumes 153 billion floating-point operations per query, bottlenecking throughput below 2 QPS and triggering catastrophic timeout cascades. Always deploy Approximate Nearest Neighbor (ANN) indices such as HNSW or IVF-PQ (Johnson et al., 2021).

    Decentralized Data Mesh & Domain Data Contracts

    In massive organizations, centralized data engineering teams become bottlenecks unable to parse evolving upstream application semantics. Data Mesh (Dehghani, 2022) decentralizes dataset ownership to domain teams who treat curated Lakehouse tables as self-serve "Data Products", governed by versioned schema contracts, SLAs, and automated federated governance.

    💻 Production Implementation: Lakehouse OCC & PQ Vector Engine

    The following typed Python program implements both an ACID Lakehouse Optimistic Concurrency Control (OCC) engine and a Product Quantization (PQ) Vector Compression calculator using Pydantic V2. It demonstrates serializable snapshot conflict detection, zero-copy time travel, and billion-vector RAM reduction calculations.

    """
Lakehouse Optimistic Concurrency Control (OCC) & Product Quantization Vector Engine.
Demonstrates ACID transaction conflict validation, historical time travel,
and billion-scale vector memory compression using Pydantic V2.
"""

from typing import Dict, List, Set, Optional, Tuple
import math
from pydantic import BaseModel, Field


# =====================================================================
# 1. Pydantic V2 Configuration & Telemetry Models
# =====================================================================

class CommitLogEntry(BaseModel):
    """Represents an atomic append-only transaction log commit in a Lakehouse."""
    version: int
    written_files: Set[str]
    deleted_files: Set[str]


class OCCValidationResult(BaseModel):
    """Telemetry outcome of an Optimistic Concurrency Control validation check."""
    committed: bool
    new_version: int
    conflicting_files: Set[str]
    status_message: str


class VectorPQConfig(BaseModel):
    """Configuration parameters for Product Quantization (PQ) compression."""
    dimension_d: int = Field(default=768, description="Original embedding vector dimension")
    subspaces_M: int = Field(default=96, description="Number of orthogonal sub-vectors")
    centroids_K: int = Field(default=256, description="Centroids per subspace (256 = 8-bit code)")


class CompressionReport(BaseModel):
    """Quantifies RAM reduction achieved by Product Quantization across billion-scale indices."""
    total_vectors: int
    raw_fp32_gb: float
    pq_compressed_gb: float
    compression_ratio: float


# =====================================================================
# 2. Lakehouse OCC & Time-Travel Engine
# =====================================================================

class LakehouseOCCEngine:
    """
    Implements an ACID Delta/Iceberg transaction log with Optimistic Concurrency
    Control (OCC) and zero-copy historical time-travel snapshot evaluation.
    """

    def __init__(self):
        self.current_version: int = 0
        self.commit_log: Dict[int, CommitLogEntry] = {}
        self.active_files: Set[str] = set()

    def begin_transaction(self) -> int:
        """Captures immutable snapshot version at transaction start."""
        return self.current_version

    def commit(
        self,
        start_version: int,
        read_files: Set[str],
        write_files: Set[str],
        delete_files: Set[str]
    ) -> OCCValidationResult:
        """
        Evaluates OCC validation predicate:
        Validate(T_i) = [ (R(T_i) | W(T_i) | D(T_i)) intersect ConcurrentModified == Empty ]
        """
        concurrent_modified: Set[str] = set()
        for v in range(start_version + 1, self.current_version + 1):
            entry = self.commit_log[v]
            concurrent_modified.update(entry.written_files)
            concurrent_modified.update(entry.deleted_files)

        conflicts = (read_files | write_files | delete_files).intersection(concurrent_modified)
        if conflicts:
            return OCCValidationResult(
                committed=False,
                new_version=self.current_version,
                conflicting_files=conflicts,
                status_message=f"OCC Conflict Abort: Overlapping mutations on {sorted(list(conflicts))}"
            )

        # Atomic commit increment
        self.current_version += 1
        self.commit_log[self.current_version] = CommitLogEntry(
            version=self.current_version,
            written_files=write_files,
            deleted_files=delete_files
        )
        self.active_files.difference_update(delete_files)
        self.active_files.update(write_files)

        return OCCValidationResult(
            committed=True,
            new_version=self.current_version,
            conflicting_files=set(),
            status_message=f"Committed Atomically at Version {self.current_version}"
        )

    def time_travel_snapshot(self, target_version: int) -> Set[str]:
        """Reconstructs exact file manifest active at historical target_version."""
        if target_version > self.current_version or target_version < 0:
            raise ValueError(f"Invalid target version: {target_version}")
        files: Set[str] = set()
        for v in range(1, target_version + 1):
            entry = self.commit_log[v]
            files.update(entry.written_files)
            files.difference_update(entry.deleted_files)
        return files


# =====================================================================
# 3. Product Quantization (PQ) Vector Compression Engine
# =====================================================================

class ProductQuantizationIndex:
    """
    Demonstrates Product Quantization subspace encoding and Asymmetric
    Distance Computation (ADC) memory compression invariants.
    """

    def __init__(self, config: VectorPQConfig):
        self.cfg = config
        if self.cfg.dimension_d % self.cfg.subspaces_M != 0:
            raise ValueError("dimension_d must be evenly divisible by subspaces_M")
        self.sub_dim = self.cfg.dimension_d // self.cfg.subspaces_M

    def calculate_compression_metrics(self, total_vectors: int = 1_000_000_000) -> CompressionReport:
        """
        Computes exact memory footprint reduction:
        C_PQ = (d * 32 bits) / (M * log2(K) bits)
        """
        bits_per_code = math.ceil(math.log2(self.cfg.centroids_K))
        raw_bytes_per_vec = self.cfg.dimension_d * 4  # FP32 = 4 bytes
        pq_bytes_per_vec = self.cfg.subspaces_M * (bits_per_code / 8.0)

        raw_total_gb = (total_vectors * raw_bytes_per_vec) / (1024 ** 3)
        pq_total_gb = (total_vectors * pq_bytes_per_vec) / (1024 ** 3)
        ratio = raw_bytes_per_vec / pq_bytes_per_vec

        return CompressionReport(
            total_vectors=total_vectors,
            raw_fp32_gb=round(raw_total_gb, 2),
            pq_compressed_gb=round(pq_total_gb, 2),
            compression_ratio=round(ratio, 2)
        )

    def quantize_mock_vector(self, vector: List[float]) -> List[int]:
        """Simulates partitioning vector into M subspaces and assigning centroid IDs."""
        if len(vector) != self.cfg.dimension_d:
            raise ValueError(f"Expected vector dimension {self.cfg.dimension_d}, got {len(vector)}")
        codes: List[int] = []
        for m in range(self.cfg.subspaces_M):
            sub_vec = vector[m * self.sub_dim : (m + 1) * self.sub_dim]
            sub_norm = sum(abs(x) for x in sub_vec) / self.sub_dim
            centroid_id = min(self.cfg.centroids_K - 1, int((sub_norm * 100) % self.cfg.centroids_K))
            codes.append(centroid_id)
        return codes

    1. The Billion-Scale RAM & Throughput Bottleneck

    Storing 5 billion 512-dimensional FP32 vectors uncompressed requires \(5 \times 10^9 \times 512 \times 4\text{ bytes} = 10.24\text{ Terabytes}\) of continuous fast memory. Simultaneously, Pinterest's mobile Lens visual search requires retrieving Top-100 nearest visual neighbors within a strict \(12\text{ millisecond}\) P99 SLA at peak traffic loads exceeding 150,000 queries per second. Disk-backed brute force scans failed latency budgets by three orders of magnitude.

    2. HNSW Graphs + Asymmetric Distance Product Quantization

    Pinterest engineered a unified vector search architecture combining HNSW proximity graphs with Asymmetric Distance Product Quantization (ADPQ) (Jégou et al., 2011): - 32x Subspace Compression: Each 512-d vector (\(2,048\text{ bytes}\)) is partitioned into \(M = 64\) subspaces quantized to 8-bit codebook centroids (\(64\text{ bytes}\) total per pin). - In-Memory HNSW Express Routing: Search requests descend the multi-layer HNSW graph in logarithmic steps, evaluating Asymmetric Distance Computation (ADC) via pre-computed lookup tables in L3 CPU cache.

    3. Quantitative Performance Outcomes

    • Memory Footprint Collapse: Total cluster memory dropped from \(10.24\text{ TB}\) down to \(320\text{ GB}\) of RAM, fitting comfortably across just 4 memory-optimized server instances.
    • Latency & Recall SLA: Sustained 150,000 QPS at sub-8ms P99 query latency while preserving \(> 95\%\) recall@10.

    1. The Parquet Random-Access Shuffling Trap

    Apache Parquet was designed for sequential OLAP analytical scans (e.g., SUM(revenue) across millions of rows). However, deep learning training loops require stochastic global random shuffling across epochs to guarantee SGD convergence. Reading a single randomly selected image tensor from Parquet forces the worker to fetch and decompress an entire \(128\text{ MB}\) row group—creating \(1000\times\) read amplification and starving expensive NVIDIA H100 GPUs of training batches.

    2. The Apache Lance Zero-Copy AI Architecture

    Engineering teams adopted Apache Lance as a next-generation columnar AI storage layer (Zaharia et al., 2021): - O(1) Random Row Indexing: Lance encodes structural offset tables directly inside file footers, enabling direct byte-range S3 GET lookups for individual multimodal rows without touching neighboring records. - Embedded Vector Indexes & ACID Versioning: Lance natively embeds IVF-PQ and HNSW vector indices alongside ACID OCC commit manifests, unifying RAG semantic filtering and PyTorch training loaders inside a single zero-copy table.

    3. Quantitative Training Acceleration

    • Random Lookup Speedup: Single-row multimodal retrieval latency fell from \(45\text{ ms}\) (Parquet) down to \(0.4\text{ ms}\) (Lance)—a \(100\times\) acceleration.
    • Accelerator Utilization: H100 GPU arithmetic utilization jumped from \(42\%\) to \(> 98\%\) with zero separate vector database synchronization lag.

    ❓ Interactive Self-Assessment Micro-Checks

    Self-Assessment 1: Calculating Exact PQ Memory Compression & RAM Footprint

    An enterprise RAG retrieval system manages a corpus of \(N = 10,000,000\) document chunk embeddings, each having dimension \(d = 1024\) stored in standard FP32 (\(4\text{ bytes/float}\)).

    To deploy the index entirely inside fast server RAM, engineers apply Product Quantization (PQ) dividing each vector into \(M = 64\) orthogonal subspaces, quantizing each subspace into \(K = 256\) centroids (\(8\text{ bits} = 1\text{ byte per code}\)).

    1. Calculate the uncompressed FP32 RAM footprint.
    2. Calculate the PQ compressed RAM footprint and the exact compression factor \(\mathcal{C}_{\text{PQ}}\).
    Reveal Detailed Solution

    Step 1: Uncompressed FP32 Memory Footprint

    Each 1024-dimensional FP32 vector consumes:

    \[ 1024 \times 4\text{ bytes} = 4,096\text{ bytes per vector} \]

    Across \(N = 10,000,000\) vectors:

    \[ \begin{aligned} \text{RAM}_{\text{raw}} &= 10^7 \times 4,096\text{ bytes} \\ &= 40,960,000,000\text{ bytes} \approx 38.15\text{ GiB } (40.96\text{ GB decimal}) \end{aligned} \]

    Step 2: PQ Compressed Memory Footprint

    With \(M = 64\) subspaces and \(K = 256\) centroids (\(\lceil \log_2 256 \rceil = 8\text{ bits} = 1\text{ byte}\) per subspace index), each vector is represented by a compact \(64\text{-byte}\) code:

    \[ \begin{aligned} \text{RAM}_{\text{PQ}} &= 10^7 \times 64\text{ bytes} \\ &= 640,000,000\text{ bytes} \approx 610.35\text{ MiB } (0.64\text{ GB decimal}) \end{aligned} \]

    (Note: Storing the \(M=64\) centroid codebooks themselves requires only \(64 \times 256 \times (1024/64) \times 4 = 1\text{ MB}\), which is negligible).

    Step 3: Compression Ratio \(\mathcal{C}_{\text{PQ}}\) (Definition 12.10.4)

    \[ \mathcal{C}_{\text{PQ}} = \frac{4 d}{M} = \frac{4 \times 1024}{64} = 64\times \text{ memory reduction} \]

    Conclusion: PQ shrinks the index from \(40.96\text{ GB}\) down to \(0.64\text{ GB}\) (\(64\times\) compression), enabling the entire 10-million-vector index to reside inside fast CPU cache for sub-millisecond search.

    Self-Assessment 2: Evaluating Lakehouse OCC Validation Intersection

    A Delta Lake table at snapshot version \(v_5\) contains active Parquet files \(\{f_1, f_2, f_3, f_4\}\). Two automated compute pipelines start concurrently at \(v_5\): - Transaction \(T_A\) (Schema Backfill): Reads \(\{f_1, f_2\}\), plans to write \(\{f_5\}\), and mark \(\{f_1\}\) deleted. - Transaction \(T_B\) (Compaction Daemon): Reads \(\{f_2, f_3\}\), plans to write compacted file \(\{f_6\}\), and mark \(\{f_2, f_3\}\) deleted.

    Suppose Transaction \(T_B\) finishes first and commits at version \(v_6\).

    Evaluate the OCC Validation Predicate (Definition 12.10.1) when Transaction \(T_A\) subsequently attempts to commit. Must \(T_A\) commit or abort? Explain why.

    Reveal Detailed Solution

    Step 1: Identify Concurrent Modifications at \(v_6\)

    Transaction \(T_B\) committed at \(v_6\) with:

    \[ \mathcal{W}_{\text{committed}}(v_6) = \{f_6\}, \quad \mathcal{D}_{\text{committed}}(v_6) = \{f_2, f_3\} \]

    Therefore, the total modified set introduced after \(v_5\) is:

    \[ \mathcal{M}_{v_6} = \{f_2, f_3, f_6\} \]

    Step 2: Evaluate \(T_A\)'s Access Footprint

    Transaction \(T_A\)'s read, write, and delete footprint is:

    \[ \begin{aligned} \mathcal{A}(T_A) &= \mathcal{R}(T_A) \cup \mathcal{W}(T_A) \cup \mathcal{D}(T_A) \\ &= \{f_1, f_2\} \cup \{f_5\} \cup \{f_1\} = \{f_1, f_2, f_5\} \end{aligned} \]

    Step 3: Compute OCC Intersection (Definition 12.10.1)

    \[ \mathcal{A}(T_A) \cap \mathcal{M}_{v_6} = \{f_1, f_2, f_5\} \cap \{f_2, f_3, f_6\} = \{f_2\} \neq \emptyset \]

    Conclusion: Because the intersection contains file \(f_2\) (which \(T_A\) read to compute its backfill while \(T_B\) concurrently compacted and deleted \(f_2\)), the OCC Validation Predicate evaluates to FALSE. Transaction \(T_A\) MUST ABORT and retry reading the newly committed snapshot \(v_6\) (where file \(f_6\) now represents \(f_2\)'s data), strictly preventing silent data corruption or duplicate rows.
