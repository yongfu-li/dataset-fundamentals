    🎯 Conceptual Overview & Theoretical Foundations

    While dataset versioning provides indispensable guarantees for model provenance, auditability, and experimentation reproducibility (Sculley et al., 2015), real-world production deployments confront severe engineering and regulatory headwinds. High-velocity streaming ingestion—frequently buffered by distributed logs like Apache Kafka (Wang et al., 2015) and processed via distributed analytics frameworks like Apache Spark (Zaharia et al., 2016)—creates millions of discrete micro-batch files. This phenomenon, known as the small-file problem, cripples analytical query engines, degrades distributed filesystems (Shvachko et al., 2010), and inflates cloud object storage API transaction costs (Armbrust et al., 2020).

    Simultaneously, privacy and compliance frameworks—most notably the European Union General Data Protection Regulation (GDPR) Article 17 ("Right to be Forgotten"), the California Consumer Privacy Act (CCPA), and HIPAA de-identification rules (Villaronga et al., 2018; Politou et al., 2018)—directly contradict the immutable append-only foundation of Content-Addressable Storage (CAS). When an individual exercises their legal right to data erasure, purging their records from historical, cryptographically signed dataset releases imposes catastrophic write amplification and storage rewriting overhead (Hermann & Balso, 2017).

    To balance these conflicting demands, modern data lakehouse architectures decouple logical row deletions from physical data rewrites via Deletion Vectors, consolidate streaming micro-batches through Bin-Packing Compaction, and apply Automated Retention Lifecycle Tiers to prune unreferenced orphan snapshots.

    Definition 12.7.1: Small-File Query Latency Degradation & HTTP Overhead

    Let an analytical dataset of total data volume \(V\) be partitioned across \(N\) distinct physical objects \(\{f_1, f_2, \dots, f_N\}\) stored in a cloud object store (e.g., AWS S3, Google Cloud Storage). Accessing any individual object over HTTPS imposes a fixed network round-trip handshake and metadata resolution latency \(t_{\text{req}} \in [15\text{ ms}, 40\text{ ms}]\) (Armbrust et al., 2020).

    Given an aggregate client-to-storage network streaming bandwidth \(B_{\text{stream}}\), the total query scan duration \(T_{\text{scan}}\) across \(N\) files is:

    \[ T_{\text{scan}} = \sum_{i=1}^N \left( t_{\text{req}} + \frac{S_i}{B_{\text{stream}}} \right) = N \cdot t_{\text{req}} + \frac{V}{B_{\text{stream}}} \]

    where \(S_i\) is the byte size of file \(i\), and \(V = \sum_{i=1}^N S_i\).

    Overhead Ratio & Asymptotic Collapse

    Let \(\bar{S} = V / N\) denote the average file size. The fraction of total query wall-clock time consumed purely by HTTP handshake and metadata overhead \(\Phi_{\text{overhead}}\) is:

    \[ \Phi_{\text{overhead}} = \frac{N \cdot t_{\text{req}}}{N \cdot t_{\text{req}} + \frac{V}{B_{\text{stream}}}} = \frac{t_{\text{req}}}{t_{\text{req}} + \frac{\bar{S}}{B_{\text{stream}}}} \]

    As the streaming ingestion frequency increases and file size shrinks (\(\bar{S} \to 0\)):

    \[ \lim_{\bar{S} \to 0} \Phi_{\text{overhead}} = 1.0 \quad (100\% \text{ latency spent on connection handshakes}) \]

    For example, scanning \(V = 100\text{ GB}\) stored as \(N = 100,000\) micro-files of \(1\text{ MB}\) each with \(t_{\text{req}} = 25\text{ ms}\) and \(B_{\text{stream}} = 1\text{ GB/s}\) yields: - Pure data transfer time: \(100\text{ GB} / 1\text{ GB/s} = 100\text{ seconds}\). - Connection overhead time: \(100,000 \times 0.025\text{ s} = 2,500\text{ seconds } (\approx 41.6\text{ minutes})\). - Overhead ratio: \(\Phi_{\text{overhead}} = 2500 / 2600 \approx 96.15\%\).

    Definition 12.7.2: Bin-Packing Compaction Speedup & Optimal Target Sizing

    Bin-packing compaction coalesces \(N_{\text{small}}\) fragmented micro-files into \(M = \lceil V / S_{\text{target}} \rceil\) consolidated columnar segments, where \(S_{\text{target}} \gg \bar{S}\).

    The theoretical query scan acceleration factor \(\mathcal{S}_{\text{compaction}}\) achieved by compaction is:

    \[ \mathcal{S}_{\text{compaction}} = \frac{T_{\text{scan, uncompacted}}}{T_{\text{scan, compacted}}} = \frac{N_{\text{small}} \cdot t_{\text{req}} + \frac{V}{B_{\text{stream}}}}{\left\lceil \frac{V}{S_{\text{target}}} \right\rceil \cdot t_{\text{req}} + \frac{V}{B_{\text{stream}}}} \]

    Optimal Target Segment Sizing (\(S_{\text{target}}^*\))

    The choice of \(S_{\text{target}}\) represents a fundamental trade-off: 1. Lower Bound (\(S_{\text{target}} \ge 128\text{ MB}\)): Large enough to amortize \(t_{\text{req}}\) to \(< 1\%\) of total scan time and maximize Parquet row-group dictionary encoding and vectorized SIMD decoding (Armbrust et al., 2020). 2. Upper Bound (\(S_{\text{target}} \le 512\text{ MB} - 1\text{ GB}\)): Small enough to allow granular predicate pushdown pruning (skipping entire blocks via min/max zone maps) and fit within single-core CPU executor memory without triggering garbage collection thrashing.

    Consolidating \(100,000\) micro-files (\(100\text{ GB}\)) into \(M = 400\) blocks of \(S_{\text{target}} = 256\text{ MB}\) slashes connection overhead from \(2,500\text{ s}\) down to \(10\text{ s}\), delivering an empirical end-to-end speedup of:

    \[ \mathcal{S}_{\text{compaction}} = \frac{2500 + 100}{10 + 100} = \frac{2600}{110} \approx 23.64\times \]

    Definition 12.7.3: Object Storage API Cost Explosion Model

    Cloud object storage financial pricing models charge independently for raw persistent byte volume and transactional HTTP request verbs: - \(C_{\text{storage}}\): Cost per gigabyte-month (e.g., \(\text{USD } 0.023 / \text{GB-month}\) for AWS S3 Standard). - \(C_{\text{PUT}}\): Cost per write transaction (e.g., \(\text{USD } 0.005 / 1,000 \text{ requests} = \text{USD } 5 \times 10^{-6} / \text{req}\)). - \(C_{\text{GET}}\): Cost per read transaction (e.g., \(\text{USD } 0.0004 / 1,000 \text{ requests} = \text{USD } 4 \times 10^{-7} / \text{req}\)).

    Let an ingestion pipeline ingest total volume \(\lambda_{\text{ingest}}\) GB per month divided into micro-files of size \(S_{\text{micro}}\) MB. Let the dataset be queried \(Q\) times per month, where each query executes a full-dataset scan across all \(N\) files. The total monthly cloud storage bill \(C_{\text{monthly}}\) is:

    \[ C_{\text{monthly}} = C_{\text{storage}} \cdot V + C_{\text{PUT}} \cdot \left( \frac{\lambda_{\text{ingest}} \times 1024}{S_{\text{micro}}} \right) + C_{\text{GET}} \cdot \left( Q \cdot \frac{V \times 1024}{S_{\text{micro}}} \right) \]

    The Transaction Cost Inflection Point

    Transactional request fees surpass static byte storage costs when:

    \[ C_{\text{PUT}} \cdot \left( \frac{\lambda_{\text{ingest}} \times 1024}{S_{\text{micro}}} \right) + C_{\text{GET}} \cdot \left( Q \cdot \frac{V \times 1024}{S_{\text{micro}}} \right) > C_{\text{storage}} \cdot V \]

    When file sizes shrink below \(100\text{ KB}\) (\(S_{\text{micro}} < 0.1\text{ MB}\)), transactional HTTP GET and PUT request charges routinely exceed static byte storage expenses by over \(300\%\) (Hermann & Balso, 2017).

    Definition 12.7.4: Compliance Erasure Write Amplification & Deletion Vector Amortization

    Under data privacy regulations such as GDPR Article 17 ("Right to Erasure") and CCPA, a data subject may demand the immediate, verifiable excision of their records \(R_{\text{target}}\) from an organization's dataset archives (Villaronga et al., 2018; Politou et al., 2018).

    Synchronous File Rewrite Amplification

    Because cloud object storage files and Content-Addressable Storage blobs are strictly immutable, in-place deletion is impossible. In a naive versioning architecture, purging a single record of size \(S_{\text{record}}\) requires reading the entire containing file of size \(S_{\text{file}}\), filtering out the record in memory, and re-serializing a new physical file version. The immediate Erasure Write Amplification Factor \(\Omega_{\text{GDPR}}\) is:

    \[ \Omega_{\text{GDPR}} = \frac{S_{\text{file}}}{S_{\text{record}}} \]

    For a \(500\text{-byte}\) user record residing in a \(256\text{ MB}\) Parquet block:

    \[ \Omega_{\text{GDPR}} = \frac{256 \times 1024 \times 1024\text{ bytes}}{500\text{ bytes}} \approx 536,871\times \]

    Rewriting \(256\text{ MB}\) of data across cloud storage to purge \(500\text{ bytes}\) is computationally unsustainable when processing thousands of user revocation notices monthly.

    Deletion Vector Bitmap Amortization

    Modern Lakehouse formats (Delta Lake, Apache Iceberg) decouple logical deletion from physical file rewriting through Deletion Vectors (Armbrust et al., 2020). An erasure request writes a compressed Roaring Bitmap entry \(\mathbf{b}_{\text{del}}\) of size \(S_{\text{bitmap}} \approx 64\text{ bytes}\) to the transaction log, masking row offset \(i\):

    \[ \Omega_{\text{bitmap}} = \frac{S_{\text{bitmap}}}{S_{\text{record}}} = \frac{64\text{ bytes}}{500\text{ bytes}} = 0.128 \ll 1.0 \]

    Analytical query engines apply the bitmap as an in-memory bitmask during vectorized Parquet scanning. Physical file rewrites are deferred to scheduled bi-monthly compaction maintenance windows, amortizing the write amplification across all accumulated batch mutations:

    \[ \bar{\Omega}_{\text{amortized}} = 1 + \frac{\sum_{j=1}^{K_{\text{del}}} S_{\text{record}}^{(j)}}{S_{\text{file}}} \approx 1.05 - 1.15\times \]

    Industrial Best Practice: Automated Garbage Collection and Retention Tiers

    In high-velocity machine learning teams, automated pipelines spawn hundreds of experimental snapshots weekly. Establish automated Lifecycle Garbage Collection (GC) policies: prune unreferenced intermediate staging commits older than 14 days, while permanently locking signed, production-tagged benchmark releases (v1.0-gold) (Sculley et al., 2015).

    Common Pitfall / Anti-Pattern: Incomplete Artifact Pinning in Reproducibility Claims

    Claiming a model is reproducible by committing model weights and training code to Git while leaving the training dataset un-pinned is invalid. If upstream data lakes undergo partition compaction, row deletion, or late-arriving streaming insertions, re-running the training pipeline will produce divergent model weights.

    Cryptographic Shredding for Historical Immutable Backups

    When data subject records reside in historical, immutable, write-once-read-many (WORM) compliant archives, physical rewriting is mathematically or legally prohibited. Organizations implement Cryptographic Shredding: each user's sensitive features are encrypted with an individual Data Encryption Key (DEK). To comply with erasure requests, the organization permanently destroys the user's specific DEK, rendering their historical data ciphertext irreversibly unrecoverable (Villaronga et al., 2018).

    💻 Production Implementation: Dataset Compactor & Compliance Engine

    The following typed Python program implements a production-grade Dataset Compaction & Compliance Erasure Engine using Pydantic V2. It demonstrates streaming micro-batch ingestion, bin-packing compaction, query scan latency benchmarking, AWS S3 financial cost modeling, and GDPR tombstone deletion vectors.

    """
Dataset Compaction & Compliance Erasure Engine.
Demonstrates small-file bin-packing, query latency modeling, S3 transaction cost analysis,
and GDPR deletion vector tombstones with Pydantic V2.
"""

from typing import Dict, List, Optional, Tuple, Any
import math
from pydantic import BaseModel, Field


# =====================================================================
# 1. Pydantic V2 Telemetry & Cost Models
# =====================================================================

class MicrobatchFile(BaseModel):
    """Represents an uncompacted micro-batch file in cloud object storage."""
    file_id: str
    size_mb: float
    row_count: int


class CompactedBlock(BaseModel):
    """Represents a consolidated, bin-packed columnar Parquet segment."""
    block_id: str
    size_mb: float
    row_count: int
    constituent_file_count: int


class TombstoneRecord(BaseModel):
    """Represents a soft-deletion tombstone vector entry for compliance erasure."""
    record_uuid: str
    block_id: str
    row_index: int
    is_purged_physically: bool = False


class S3CostReport(BaseModel):
    """Monthly cloud object storage financial cost model breakdown."""
    total_volume_gb: float
    storage_cost_usd: float
    put_request_cost_usd: float
    get_request_cost_usd: float
    total_monthly_usd: float
    api_to_storage_ratio: float


# =====================================================================
# 2. Core Compaction & Compliance Engine Implementation
# =====================================================================

class DatasetCompactionAndComplianceEngine:
    """
    Simulates production Lakehouse file compaction (Delta/Iceberg bin-packing),
    query scan latency models, S3 transaction cost models, and GDPR tombstone vectors.
    """

    def __init__(self, t_req_sec: float = 0.025, network_gb_sec: float = 1.0):
        self.t_req = t_req_sec  # 25 ms per S3 GET metadata & handshake
        self.network_bandwidth = network_gb_sec  # 1.0 GB/s network throughput
        self.uncompacted_files: List[MicrobatchFile] = []
        self.compacted_blocks: List[CompactedBlock] = []
        self.tombstone_registry: Dict[str, TombstoneRecord] = {}

    def load_streaming_microbatches(self, count: int, size_mb: float, rows_per_file: int = 1000):
        """Simulates ingestion of high-frequency streaming micro-batch files."""
        self.uncompacted_files = [
            MicrobatchFile(
                file_id=f"part_{i:06d}.parquet",
                size_mb=size_mb,
                row_count=rows_per_file
            )
            for i in range(count)
        ]

    def calculate_scan_latency(self, use_compacted: bool = False) -> float:
        """
        Calculates total query scan duration:
        T_scan = N * t_req + V / B_stream
        """
        if use_compacted:
            num_files = len(self.compacted_blocks)
            total_vol_mb = sum(b.size_mb for b in self.compacted_blocks)
        else:
            num_files = len(self.uncompacted_files)
            total_vol_mb = sum(f.size_mb for f in self.uncompacted_files)

        total_vol_gb = total_vol_mb / 1024.0
        transfer_time = total_vol_gb / self.network_bandwidth
        overhead_time = num_files * self.t_req
        return overhead_time + transfer_time

    def compact_files(self, target_size_mb: float = 256.0) -> List[CompactedBlock]:
        """
        Bin-packs small micro-batch files into target-sized consolidated columnar blocks.
        """
        total_vol_mb = sum(f.size_mb for f in self.uncompacted_files)
        total_rows = sum(f.row_count for f in self.uncompacted_files)
        num_blocks = math.ceil(total_vol_mb / target_size_mb)

        self.compacted_blocks = []
        files_per_block = math.ceil(len(self.uncompacted_files) / max(1, num_blocks))

        for b_idx in range(num_blocks):
            allocated_mb = min(target_size_mb, total_vol_mb - (b_idx * target_size_mb))
            block_rows = min(total_rows // num_blocks, total_rows)
            self.compacted_blocks.append(CompactedBlock(
                block_id=f"compacted_seg_{b_idx:04d}.parquet",
                size_mb=allocated_mb,
                row_count=block_rows,
                constituent_file_count=files_per_block
            ))
        return self.compacted_blocks

    def calculate_monthly_s3_cost(
        self,
        daily_queries: int = 100,
        monthly_ingest_gb: float = 500.0,
        is_compacted: bool = False
    ) -> S3CostReport:
        """
        Models AWS S3 Standard pricing:
        - Storage: USD 0.023 / GB-month
        - PUT requests: USD 0.005 / 1,000 requests (USD 5e-6 / req)
        - GET requests: USD 0.0004 / 1,000 requests (USD 4e-7 / req)
        """
        c_storage_unit = 0.023
        c_put_unit = 0.000005
        c_get_unit = 0.0000004

        if is_compacted and self.compacted_blocks:
            file_count = len(self.compacted_blocks)
        else:
            file_count = max(1, len(self.uncompacted_files))

        total_gb = monthly_ingest_gb
        storage_cost = total_gb * c_storage_unit
        # Each ingested micro-file incurred 1 PUT
        put_cost = len(self.uncompacted_files) * c_put_unit
        # Each query scans all files in the partition
        monthly_gets = daily_queries * 30 * file_count
        get_cost = monthly_gets * c_get_unit

        total_monthly = storage_cost + put_cost + get_cost
        api_ratio = (put_cost + get_cost) / max(0.001, storage_cost)

        return S3CostReport(
            total_volume_gb=round(total_gb, 2),
            storage_cost_usd=round(storage_cost, 2),
            put_request_cost_usd=round(put_cost, 2),
            get_request_cost_usd=round(get_cost, 2),
            total_monthly_usd=round(total_monthly, 2),
            api_to_storage_ratio=round(api_ratio, 2)
        )

    def execute_compliance_erasure(
        self,
        record_uuid: str,
        target_block_id: str,
        row_offset: int,
        use_deletion_vector: bool = True
    ) -> Dict[str, Any]:
        """
        Compares synchronous physical rewriting vs. Delta Lake deletion vector tombstones.
        """
        block_bytes = 256 * 1024 * 1024  # 256 MB Parquet block
        record_bytes = 500               # 500 bytes user record

        if use_deletion_vector:
            # Soft delete: append 64-byte Roaring Bitmap entry to transaction log
            tombstone = TombstoneRecord(
                record_uuid=record_uuid,
                block_id=target_block_id,
                row_index=row_offset,
                is_purged_physically=False
            )
            self.tombstone_registry[record_uuid] = tombstone
            bytes_written = 64
            write_amplification = bytes_written / record_bytes
            latency_ms = 1.2
            method = "Deletion Vector Bitmap (Deferred)"
        else:
            # Synchronous rewrite: must re-write the entire 256 MB file to delete 500 bytes
            bytes_written = block_bytes
            write_amplification = block_bytes / record_bytes
            latency_ms = 4500.0
            method = "Synchronous File Rewrite (Naive)"

        return {
            "record_uuid": record_uuid,
            "method": method,
            "bytes_written": bytes_written,
            "write_amplification": round(write_amplification, 2),
            "latency_ms": latency_ms
        }

    1. The Compliance Conflict & Naive Failure

    Under HIPAA de-identification standards and GDPR Article 17, when a patient revokes research consent, all their associated clinical records must be excised across all historical training splits.

    Initially, the health platform executed naive synchronous Parquet rewriting: whenever an erasure request arrived, a Spark job scanned the \(80\text{ TB}\) lake, identified the target patient UUID, and re-wrote every containing \(256\text{ MB}\) Parquet block. After receiving 45 consent revocations in a single month, continuous background I/O thrashing halted active model training runs, and monthly cloud rewriting bills spiked by \(\text{USD } 72,000\).

    2. The Architectural Resolution

    The platform transitioned to Delta Lake Deletion Vectors (Armbrust et al., 2020) combined with Cryptographic Shredding (Villaronga et al., 2018): - Sub-Second Soft Deletions: Erasure requests append a 64-byte Roaring Bitmap to the Delta transaction log, masking patient records without touching physical Parquet storage. - Per-Subject Key Shredding: Highly sensitive genomic features are encrypted with patient-specific Data Encryption Keys (DEKs). Upon revocation, destroying the patient's individual DEK renders all historical ciphertext permanently indecipherable across immutable historical backups. - Consolidated Maintenance: Physical block rewriting is deferred to an automated bi-monthly batch compaction job, consolidating hundreds of accumulated revocations into a single pass.

    3. Quantitative Results & Operational Savings

    • Write Amplification Reduction: Immediate write amplification collapsed from \(536,871\times\) down to \(0.13\times\) (an amortized \(1.15\times\) during batch vacuum).
    • Financial Cost Savings: Cloud rewriting expenses dropped from \(\text{USD } 72,000\text{/month}\) down to under \(\text{USD } 4,300\text{/month}\)—a \(94\%\) expenditure reduction.

    2. The Compaction & Lifecycle Architecture

    ❓ Interactive Self-Assessment Micro-Checks

    Self-Assessment 1: Inode Table Exhaustion Analysis and POSIX Scaling Limits

    A computer vision machine learning team stores \(100\text{ Million}\) small JPEG images (\(15\text{ KB}\) average size) on an on-premises Linux server using an EXT4 filesystem with default formatting parameters (\(1\text{ inode per } 16\text{ KB}\) of disk space, total storage capacity \(2\text{ TB}\)).

    1. Calculate the total byte volume consumed by the images.
    2. Explain why the operating system suddenly throws No space left on device errors when saving image 100,000,001, even though the disk reports over \(500\text{ GB}\) of free storage space.
    3. How does packaging images into container formats (e.g., WebDataset TAR archives or Apache Parquet blocks) resolve this issue?
    Reveal Detailed Solution

    Step 1: Compute Total Byte Volume $\(V_{\text{bytes}} = 100,000,000 \times 15\text{ KB} = 1,500,000,000\text{ KB} \approx 1.5\text{ Terabytes}\)$ On a \(2.0\text{ TB}\) disk, \(2.0 - 1.5 = 0.5\text{ TB} = 500\text{ GB}\) of physical disk space remains completely unwritten.

    Step 2: Diagnose Inode Exhaustion In traditional POSIX Linux filesystems (EXT4), every physical file and directory requires an entry in the pre-allocated filesystem inode table. The total number of inodes created during filesystem formatting is: $\(N_{\text{inodes}} = \frac{\text{Total Capacity}}{\text{Inode Ratio}} = \frac{2 \times 10^{12}\text{ bytes}}{16,384\text{ bytes/inode}} \approx 122,070,312\text{ inodes}\)$ When factoring in directory structures, metadata files, and temporary OS files, all \(122\text{ Million}\) inodes are exhausted once the 100 million image files are written. The Linux kernel returns ENOSPC (No space left on device) whenever the inode table is saturated, regardless of available byte capacity.

    Step 3: Architectural Resolution Packaging images into contiguous container files (e.g., WebDataset TAR archives containing 10,000 images each or 256 MB Parquet blocks) reduces the physical filesystem file count from \(100,000,000\) down to \(10,000\) files. This consumes only \(10,000\) inodes, eliminating filesystem metadata exhaustion while accelerating sequential I/O by orders of magnitude.

    Self-Assessment 2: Calculating Exact Monthly S3 Savings from Compaction Bin-Packing

    A real-time IoT feature lake ingests \(\lambda_{\text{ingest}} = 1,000\text{ GB}\) of Parquet telemetry monthly in \(S_{\text{micro}} = 200\text{ KB}\) micro-batch files (\(S_{\text{micro}} \approx 0.1953\text{ MB}\)). The dataset is queried \(Q = 200\) times per month by analytical training pipelines.

    Using the S3 Cost Model (Definition 12.7.3) with: - \(C_{\text{storage}} = \text{USD } 0.023 / \text{GB-month}\) - \(C_{\text{PUT}} = \text{USD } 0.005 / 1,000\text{ requests}\) (\(\text{USD } 5 \times 10^{-6}/\text{req}\)) - \(C_{\text{GET}} = \text{USD } 0.0004 / 1,000\text{ requests}\) (\(\text{USD } 4 \times 10^{-7}/\text{req}\))

    1. Calculate the monthly bill under uncompacted streaming.
    2. Calculate the monthly bill if an automated compactor consolidates files into \(S_{\text{target}} = 256\text{ MB}\) blocks immediately after ingestion.
    Reveal Detailed Solution

    Step 1: Uncompacted Monthly S3 Cost - Total File Count: $\(N_{\text{uncomp}} = \frac{1,000\text{ GB} \times 1,024\text{ MB/GB}}{0.1953125\text{ MB/file}} = 5,242,880\text{ files}\)$ - Static Storage Cost: $\(C_{\text{storage}} = 1,000\text{ GB} \times \text{USD } 0.023 = \text{USD } 23.00\)$ - Ingestion PUT Request Cost: $\(C_{\text{PUT}} = 5,242,880 \times \text{USD } 5 \times 10^{-6} = \text{USD } 26.21\)$ - Query GET Request Cost (\(Q = 200\) queries across all files): $\(N_{\text{GET}} = 200 \times 5,242,880 = 1,048,576,000\text{ GET requests}\)$ $\(C_{\text{GET}} = 1,048,576,000 \times \text{USD } 4 \times 10^{-7} = \text{USD } 419.43\)$ - Total Uncompacted Monthly Bill: $\(C_{\text{total, uncomp}} = 23.00 + 26.21 + 419.43 = \text{USD } 468.64\)$ Notice that GET query requests account for \(\frac{419.43}{468.64} \approx 89.5\%\) of the total cloud bill!

    Step 2: Compacted Monthly S3 Cost (\(S_{\text{target}} = 256\text{ MB}\)) - Consolidated Block Count: $\(N_{\text{compacted}} = \frac{1,000\text{ GB} \times 1,024\text{ MB/GB}}{256\text{ MB}} = 4,000\text{ blocks}\)$ - Static Storage Cost: \(\text{USD } 23.00\) - Ingestion PUT Cost: \(\text{USD } 26.21\) (assuming micro-batches still ingested, or compacted in memory) - Compaction Write PUTs: \(4,000 \times \text{USD } 5 \times 10^{-6} \approx \text{USD } 0.02\) - Query GET Request Cost (\(Q = 200\) queries across \(4,000\) blocks): $\(N_{\text{GET, comp}} = 200 \times 4,000 = 800,000\text{ GET requests}\)$ $\(C_{\text{GET, comp}} = 800,000 \times \text{USD } 4 \times 10^{-7} = \text{USD } 0.32\)$ - Total Compacted Monthly Bill: $\(C_{\text{total, comp}} = 23.00 + 26.21 + 0.02 + 0.32 = \text{USD } 49.55\)$

    Conclusion: Automated compaction slashes monthly GET request costs from \(\text{USD } 419.43\) to \(\text{USD } 0.32\) (\(99.9\%\) reduction), reducing the total monthly object storage bill from \(\text{USD } 468.64\) down to \(\text{USD } 49.55\)—saving \(\text{USD } 419.09\text{/month}\) (\(89.4\%\) overall savings) while accelerating queries by \(> 20\times\).
