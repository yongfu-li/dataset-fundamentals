    🎯 Conceptual Overview & Theoretical Foundations

    Standard software version control systems such as Git were architected for small, diffable, plain-text source files. When applied to machine learning datasets—which feature massive binary files, high-cardinality tensors, and multi-gigabyte embeddings—traditional Git repositories choke: the internal object database duplicates entire binary files upon each minor mutation, quickly degrading clone, push, and checkout operations to unusable levels (Pacheco et al., 2024).

    To overcome these physical bottlenecks, modern dataset versioning decouples the control plane (lightweight Git tracking metadata, pointer files, and Merkle DAG commits) from the data plane (immutable Content-Addressable Storage residing in scalable cloud object stores) (Einziger et al., 2021), unified across modern Lakehouse architectures (Armbrust et al., 2020), versioned relational databases like OrpheusDB (Huang et al., 2017), and ML lifecycle registries like MLflow (Zaharia et al., 2018).

    Modern dataset versioning platforms—including Data Version Control (DVC) (Pacheco et al., 2024), LakeFS (Einziger et al., 2021), and Delta Lake (Armbrust et al., 2020)—enforce four core architectural primitives: 1. Content-Addressable Storage (CAS): Payloads are identified exclusively by their cryptographic hash digest, guaranteeing universal immutability and automatic deduplication. 2. Merkle DAG Directory Trees: Snapshots are represented as hierarchical trees of hashes, enabling sub-tree reuse and logarithmic diffing. 3. Zero-Copy Branching: Development branches are isolated metadata namespaces pointing to immutable storage objects, requiring zero data duplication. 4. Content-Defined Chunking (CDC): Large continuous binary files are partitioned into variable-length chunks via rolling hashes, preserving deduplication across byte-shift mutations (Rabin, 1981; Xia et al., 2016).

    Definition 12.6.1: Content-Addressable Storage (CAS) & Cryptographic Collision Resistance

    In Content-Addressable Storage (CAS), an arbitrary immutable data payload \(B \in \{0, 1\}^*\) is addressed strictly by its cryptographic digest \(h\) computed via a collision-resistant hash function \(\mathcal{H}: \{0, 1\}^* \to \{0, 1\}^b\) (such as SHA-256, where \(b = 256\) bits) (Merkle, 1987):

    \[ h = \mathcal{H}(B) = \text{SHA-256}(B) \]

    The storage layer enforces the Universal Immutability Invariant: for any two files \(B_1\) and \(B_2\), their physical storage addresses are identical if and only if their binary contents are identical:

    \[ \mathcal{H}(B_1) = \mathcal{H}(B_2) \iff B_1 = B_2 \]

    Cryptographic Collision Resistance Bound

    By the generalized Birthday Paradox, if a distributed dataset storage pool ingests \(q\) distinct binary objects, the probability of encountering at least one hash collision is bounded by:

    \[ \Pr[\text{Collision}] \le \frac{q(q - 1)}{2^{b + 1}} \approx \frac{q^2}{2^{b + 1}} \]

    For SHA-256 (\(b = 256\)), storing \(q = 10^{15}\) (one quadrillion) distinct dataset files yields:

    \[ \Pr[\text{Collision}] \le \frac{(10^{15})^2}{2^{257}} \approx \frac{10^{30}}{2.31 \times 10^{77}} \approx 4.3 \times 10^{-48} \]

    This probability is vastly lower than the rate of uncorrectable cosmic-ray-induced memory bitflips, guaranteeing that content addresses function as globally unique, immutable object identifiers.

    Definition 12.6.2: Merkle DAG Directory Trees & Canonical Manifest Invariants

    A dataset snapshot containing \(M\) files distributed across a directory hierarchy is represented as a Merkle Directed Acyclic Graph (DAG) \(\mathcal{G} = (\mathcal{V}, \mathcal{E})\) (Merkle, 1987). Leaf nodes represent raw data blobs, while interior nodes represent directory manifests.

    The cryptographic digest of an interior directory node \(N_v\) having child elements \(\{c_1, c_2, \dots, c_k\}\) is computed recursively as:

    \[ \mathcal{H}(N_v) = \mathcal{H}\left( \text{metadata}(N_v) \mathbin{\Vert} \bigoplus_{i=1}^k \left( \text{name}(c_i) \mathbin{\Vert} \mathcal{H}(c_i) \mathbin{\Vert} \text{size}(c_i) \right) \right) \]

    where \(\|\) denotes string concatenation and \(\oplus\) denotes deterministic canonical sort ordering by filename.

    Canonical Manifest Properties

    1. Sub-Tree Structural Sharing: If revision \(V_{k+1}\) modifies only a single file \(f \in \text{Dir}_A\), all other directories \(\text{Dir}_B, \text{Dir}_C\) retain their exact Merkle sub-tree digests:
    \[ \mathcal{H}(\text{Dir}_B^{(V_{k+1})}) = \mathcal{H}(\text{Dir}_B^{(V_k)}) \]
    1. Logarithmic Diffing Complexity: Comparing two complete dataset snapshots \(V_1\) and \(V_2\) containing \(M\) files does not require scanning all \(M\) files. Traversal immediately terminates along any branch where \(\mathcal{H}(N_v^{(V_1)}) = \mathcal{H}(N_v^{(V_2)})\), reducing diffing latency from \(\mathcal{O}(M)\) down to \(\mathcal{O}(\Delta \cdot \text{depth})\), where \(\Delta\) is the number of mutated files.

    Definition 12.6.3: Storage Deduplication Ratio & Incremental Mutation Dynamics

    Consider a sequence of \(K\) historical dataset revisions \(V_1, V_2, \dots, V_K\). Let \(\mathcal{B}(V_k)\) denote the set of content-addressed blobs required to reconstruct revision \(V_k\), and let \(|b|\) denote the byte size of blob \(b\).

    The Total Logical Size of the dataset across all \(K\) versions is:

    \[ S_{\text{logical}} = \sum_{k=1}^K \sum_{b \in \mathcal{B}(V_k)} |b| \]

    The Total Physical Size stored in the CAS repository is the size of the unique set union:

    \[ S_{\text{physical}} = \sum_{b \in \bigcup_{k=1}^K \mathcal{B}(V_k)} |b| \]

    The Global Deduplication Efficiency Ratio \(\rho_{\text{dedup}}\) is defined as:

    \[ \rho_{\text{dedup}}(V_1, \dots, V_K) = 1 - \frac{S_{\text{physical}}}{S_{\text{logical}}} = 1 - \frac{\sum_{b \in \bigcup_{k=1}^K \mathcal{B}(V_k)} |b|}{\sum_{k=1}^K \sum_{b \in \mathcal{B}(V_k)} |b|} \]

    Asymptotic Convergence under Incremental Mutations

    Assume each revision introduces a fraction \(\delta \in (0, 1)\) of newly generated or modified data, while fraction \((1 - \delta)\) remains identical to the base version of size \(|V|\):

    \[ S_{\text{physical}}(K) = |V| + (K - 1) \cdot \delta \cdot |V| \]
    \[ S_{\text{logical}}(K) = K \cdot |V| \]

    Taking the limit as the number of revisions \(K \to \infty\):

    \[ \lim_{K \to \infty} \rho_{\text{dedup}} = \lim_{K \to \infty} \left( 1 - \frac{|V| + (K - 1)\delta |V|}{K |V|} \right) = 1 - \delta \]

    When \(\delta = 0.05\) (\(5\%\) mutation rate between releases), the asymptotic storage savings approach \(95\%\), proving the immense cost efficiency of content-addressable versioning over naive physical bucket copies.

    Definition 12.6.4: Content-Defined Chunking (CDC) & Rolling Rabin Fingerprint Boundaries

    Whole-file content hashing fails on large continuous binary files (e.g., SQLite databases, uncompressed TAR archives, monolithic embedding matrices): inserting a single byte at the beginning of a \(10\text{ GB}\) file alters its entire SHA-256 hash, causing the CAS repository to re-store the entire \(10\text{ GB}\) payload.

    Content-Defined Chunking (CDC) partitions a byte stream \(B = [b_0, b_1, \dots, b_{L-1}]\) into variable-length blocks using a rolling polynomial hash (Rabin Fingerprint) evaluated over a sliding window of size \(w\) (Rabin, 1981; Xia et al., 2016):

    \[ R_i = \left( \sum_{j=0}^{w-1} b_{i-j} \cdot p^j \right) \pmod M \]

    where \(p\) is an irreducible polynomial and \(M\) is a large prime modulus.

    Chunk Boundary Invariant

    A chunk boundary is cut at index \(i\) if and only if the rolling fingerprint satisfies a bitmask match:

    \[ R_i \equiv 0 \pmod D \]

    where \(D\) is the target average chunk divisor (e.g., \(D = 8\text{ KB}\) or \(64\text{ KB}\)).

    Expected Chunk Size & Boundary Re-synchronization

    Assuming rolling hash values are uniformly distributed over \(\mathbb{Z}_M\), the probability of placing a boundary cut at any byte position is:

    \[ \Pr[\text{Cut at position } i] = \frac{1}{D} \implies \mathbb{E}[\text{Chunk Size}] = D \]

    If a byte insertion of size \(\Delta x\) occurs at offset \(k\), only the single chunk spanning \([k - w, k]\) changes its boundary. Beyond that chunk, as soon as the rolling window passes through unmodified bytes, the cut condition \(R_i \equiv 0 \pmod D\) fires again at the exact same semantic boundary. The expected re-synchronization distance is bounded by:

    \[ \mathbb{E}[\text{Re-sync Distance}] \le 2D \text{ bytes} \]

    All subsequent chunks downstream retain their original content hashes, preserving deduplication across the remainder of the multi-gigabyte file.

    Industrial Best Practice: LakeFS Branching for Zero-Copy Data Environments

    When data scientists require sandboxes to test destructive cleaning pipelines on 50 TB data lakes, use LakeFS: create a copy-on-write branch (lakefs branch create dev). It spins up an isolated sandbox in 50 milliseconds with zero storage duplication, allowing safe experimentation before merging back to main (Einziger et al., 2021).

    Common Pitfall / Anti-Pattern: Manual Cloud Storage Duplication

    Copying entire cloud storage directories (aws s3 sync s3://prod s3://dev_test) to create development testbeds wastes thousands of dollars in cloud egress and storage fees, and loses all cryptographic lineage connections to production versions.

    ACID Lakehouse Logs: Delta Lake & Apache Iceberg

    While DVC and LakeFS operate primarily on file and object levels, modern Lakehouse engines (Delta Lake, Apache Iceberg) track tabular mutations at the Parquet file manifest level (Armbrust et al., 2020). Each commit appends an atomic JSON transaction log entry listing added and removed Parquet files, providing instantaneous time-travel queries (SELECT * FROM table VERSION AS OF 42) without mutating base data files.

    💻 Production Implementation: Content-Addressable Storage & Merkle DAG Engine

    The following typed Python program implements a complete Content-Addressable Storage (CAS) engine using Pydantic V2. It demonstrates immutable blob storage, Merkle DAG directory manifests, Content-Defined Chunking (CDC) with boundary re-synchronization, and zero-copy branching.

    """
Content-Addressable Storage (CAS) and Merkle DAG Engine.
Demonstrates cryptographic hashing, Merkle directory manifests,
Content-Defined Chunking (CDC), and zero-copy branching with Pydantic V2.
"""

from typing import Dict, List, Optional, Tuple, Set
import hashlib
import json
from pydantic import BaseModel, Field


# =====================================================================
# 1. Pydantic V2 Telemetry & Manifest Models
# =====================================================================

class BlobMetadata(BaseModel):
    """Metadata describing an immutable content-addressed data blob."""
    digest: str
    size_bytes: int
    content_type: str = "application/octet-stream"


class FileManifestEntry(BaseModel):
    """Describes a single file within a versioned dataset snapshot."""
    path: str
    blob_hash: str
    size_bytes: int


class MerkleManifest(BaseModel):
    """Hierarchical snapshot manifest representing a dataset revision."""
    version_tag: str
    merkle_root: str
    parent_version: Optional[str] = None
    files: List[FileManifestEntry]
    total_logical_bytes: int


class BranchDescriptor(BaseModel):
    """Tracks a zero-copy pointer to a Merkle commit in the control plane."""
    branch_name: str
    head_merkle_root: str
    created_at_version: str


# =====================================================================
# 2. Content-Addressable Storage & Merkle DAG Engine
# =====================================================================

class ContentAddressableStorageEngine:
    """
    Simulates a production-grade Content-Addressable Storage (CAS) engine
    with Merkle DAG directory manifests, zero-copy branching, and CDC chunking.
    """

    def __init__(self):
        # Physical Blob Store: hash -> raw bytes (Immutable Data Plane)
        self.blob_store: Dict[str, bytes] = {}
        # Control Plane Manifest Catalog: version_tag -> MerkleManifest
        self.catalog: Dict[str, MerkleManifest] = {}
        # Zero-Copy Branch Table: branch_name -> BranchDescriptor
        self.branches: Dict[str, BranchDescriptor] = {}

    @staticmethod
    def sha256(data: bytes) -> str:
        """Computes collision-resistant SHA-256 digest."""
        hasher = hashlib.sha256()
        hasher.update(data)
        return hasher.hexdigest()

    def put_blob(self, payload: bytes) -> str:
        """Stores a blob immutably by its content digest."""
        digest = self.sha256(payload)
        if digest not in self.blob_store:
            self.blob_store[digest] = payload
        return digest

    def get_blob(self, digest: str) -> Optional[bytes]:
        """Retrieves raw content by cryptographic hash address."""
        return self.blob_store.get(digest)

    def commit_version(
        self,
        version_tag: str,
        file_table: Dict[str, bytes],
        parent_tag: Optional[str] = None
    ) -> MerkleManifest:
        """
        Creates a Merkle DAG directory snapshot for a collection of files.
        Stores immutable data blobs and computes the canonical Merkle root digest.
        """
        entries: List[FileManifestEntry] = []
        for path in sorted(file_table.keys()):
            raw_bytes = file_table[path]
            blob_hash = self.put_blob(raw_bytes)
            entries.append(FileManifestEntry(
                path=path,
                blob_hash=blob_hash,
                size_bytes=len(raw_bytes)
            ))

        # Compute deterministic canonical Merkle root hash
        canonical_repr = [
            {"path": e.path, "hash": e.blob_hash, "size": e.size_bytes}
            for e in entries
        ]
        manifest_bytes = json.dumps(canonical_repr, sort_keys=True).encode("utf-8")
        merkle_root = self.sha256(manifest_bytes)

        manifest = MerkleManifest(
            version_tag=version_tag,
            merkle_root=merkle_root,
            parent_version=parent_tag,
            files=entries,
            total_logical_bytes=sum(e.size_bytes for e in entries)
        )
        self.catalog[version_tag] = manifest
        return manifest

    def create_branch(self, branch_name: str, from_version: str) -> BranchDescriptor:
        """
        Creates an instantaneous zero-copy branch pointing to an existing Merkle root.
        Consumes 0 bytes of physical storage.
        """
        if from_version not in self.catalog:
            raise KeyError(f"Base version '{from_version}' does not exist in catalog")
        manifest = self.catalog[from_version]
        desc = BranchDescriptor(
            branch_name=branch_name,
            head_merkle_root=manifest.merkle_root,
            created_at_version=from_version
        )
        self.branches[branch_name] = desc
        return desc

    def content_defined_chunking(self, data: bytes, target_chunk_size: int = 32) -> List[bytes]:
        """
        Implements Rabin-like Content-Defined Chunking (CDC).
        Evaluates a rolling hash window; cuts boundary when hash % target_chunk_size == 0.
        """
        chunks: List[bytes] = []
        window_size = 16
        start = 0

        p = 31
        mod = 1000000007

        rolling_hash = 0
        p_pow = 1
        for _ in range(window_size - 1):
            p_pow = (p_pow * p) % mod

        for i in range(len(data)):
            byte_val = data[i]
            rolling_hash = (rolling_hash * p + byte_val) % mod

            if i >= window_size:
                old_val = data[i - window_size]
                rolling_hash = (rolling_hash - (old_val * p_pow) % mod + mod) % mod

            # Boundary cut condition with min/max chunk size bounds
            if (rolling_hash % target_chunk_size == 0 and (i - start) >= 16) or (i - start) >= 256:
                chunks.append(data[start:i + 1])
                start = i + 1

        if start < len(data):
            chunks.append(data[start:])
        return chunks

    def calculate_deduplication_ratio(self) -> float:
        """Calculates global deduplication savings: 1 - (Physical Bytes / Logical Bytes)."""
        total_logical_bytes = sum(m.total_logical_bytes for m in self.catalog.values())
        physical_unique_bytes = sum(len(b) for b in self.blob_store.values())
        if total_logical_bytes == 0:
            return 0.0
        return 1.0 - (physical_unique_bytes / total_logical_bytes)

    1. The Multi-Modal Volume Dilemma

    A single 20-second driving clip recorded across 5 LiDAR units and 5 high-resolution cameras consumes \(2.4\text{ GB}\) of raw binary payloads. A 1,000-hour multi-sensor training corpus exceeds \(430\text{ Terabytes}\).

    Computer vision annotation teams continuously refine labels: fixing 3D bounding box dimensions, annotating occluded pedestrians, or adding HD vector map lane topologies. While the raw sensory tensors remain 100% immutable, each annotation sprint generates a new dataset release. Under naive bucket duplication (aws s3 sync s3://v1 s3://v2), creating 200 benchmark iterations would require \(200 \times 430\text{ TB} = 86\text{ Petabytes}\) of duplicate cloud storage, costing over USD 1.9 million per year in AWS S3 Standard storage fees.

    2. The Content-Addressable Storage Resolution

    The engineering team deployed Data Version Control (DVC) (Pacheco et al., 2024) backed by S3 Content-Addressable Storage: - Decoupled Control and Data Planes: The \(430\text{ TB}\) of raw sensor binaries were ingested once into S3 CAS, addressed by SHA-256 digests. - Micro-Manifest Versioning: Each new annotation release committed only a 5 MB JSON file containing bounding box coordinates and content hashes linking back to the immutable sensor frames. - Fast Local Checkouts: GPU training nodes utilized DVC hardlinks (dvc config cache.type hardlink), enabling workers to switch between 100 GB training splits in under 2 seconds without duplicating local NVMe disk blocks.

    3. Quantitative Results & Cost Reductions

    • Deduplication Efficiency: Reached a \(99.8\%\) storage deduplication ratio across 200 distinct experimental benchmark releases.
    • Annual Cloud Savings: Eliminated over USD 480,000 per year in redundant cloud object storage and data transfer fees.

    1. The Production Data Validation Hazard

    Validating complex SQL transformations, schema migrations, and deduplication logic on toy datasets rarely uncovers edge-case bugs. However, testing directly on production data lakes risks corrupting active analytics tables. Traditionally, organizations created staging environments by cloning production buckets—a process requiring \(6+\) hours to copy \(500\text{ TB}\) of data, costing thousands of dollars in egress and storage.

    2. The LakeFS Zero-Copy Branching Architecture

    By deploying LakeFS (Einziger et al., 2021) on top of S3 object storage: - Graveler SSTable Metadata Trees: LakeFS manages file manifests using immutable, sorted-string table (SSTable) key-value trees. A branch is simply an isolated pointer to a root metadata commit. - Copy-on-Write Isolation: Creating a branch (lakefs branch create dev) takes 42 milliseconds and duplicates zero bytes of S3 data. Data engineers execute destructive ETL pipelines on dev. Any modified files are written as new objects in S3; unchanged files continue referencing the shared production blobs. - Atomic Pre-Commit Hooks & Merges: Automated data quality checks run on the branch. If validation tests pass, merging dev into main is an atomic metadata operation taking under 1 second, guaranteeing zero downtime or dirty reads for downstream consumers.

    • Environment Provisioning Time: Dropped from \(6\text{ hours}\) down to \(42\text{ milliseconds}\).
    • Staging Infrastructure Cost: Reduced physical staging storage duplication costs from \(\$11,500\text{/month}\) to \(\$0\).

    ❓ Interactive Self-Assessment Micro-Checks

    Self-Assessment 1: Asymptotic Deduplication Ratio across Iterative Releases

    A deep learning dataset of base size \(|V| = 200\text{ GB}\) undergoes iterative weekly revisions. Each revision modifies or introduces exactly fraction \(\delta = 0.08\) (\(8\%\)) of new content, while the remaining \(92\%\) is identical to previous versions.

    1. Calculate the exact physical storage required in Content-Addressable Storage (CAS) after \(K = 10\) and \(K = 50\) releases, compared to a naive bucket copy approach.
    2. Determine the deduplication ratio \(\rho_{\text{dedup}}\) for \(K = 10\) and \(K = 50\).
    3. State the asymptotic deduplication efficiency as \(K \to \infty\).
    Reveal Detailed Solution

    Step 1: Compute Storage Volumes (Definition 12.6.3) - Base size: \(|V| = 200\text{ GB}\) - Mutation rate: \(\delta = 0.08\)

    Naive Bucket Copy: $\(S_{\text{naive}}(K) = K \cdot |V|\)$ - For \(K = 10\): \(S_{\text{naive}}(10) = 10 \times 200\text{ GB} = 2,000\text{ GB} = 2.0\text{ TB}\). - For \(K = 50\): \(S_{\text{naive}}(50) = 50 \times 200\text{ GB} = 10,000\text{ GB} = 10.0\text{ TB}\).

    CAS Content-Addressable Storage: $\(S_{\text{physical}}(K) = |V| + (K - 1) \cdot \delta \cdot |V| = |V| \cdot [1 + (K - 1)\delta]\)$ - For \(K = 10\): $\(S_{\text{physical}}(10) = 200 \times [1 + (10 - 1) \times 0.08] = 200 \times [1 + 0.72] = 200 \times 1.72 = 344\text{ GB}\)$ - For \(K = 50\): $\(S_{\text{physical}}(50) = 200 \times [1 + (50 - 1) \times 0.08] = 200 \times [1 + 3.92] = 200 \times 4.92 = 984\text{ GB} \approx 0.984\text{ TB}\)$

    Step 2: Calculate Deduplication Efficiency \(\rho_{\text{dedup}}\) $\(\rho_{\text{dedup}}(K) = 1 - \frac{S_{\text{physical}}(K)}{S_{\text{naive}}(K)}\)$ - For \(K = 10\): $\(\rho_{\text{dedup}}(10) = 1 - \frac{344\text{ GB}}{2,000\text{ GB}} = 1 - 0.172 = 0.828 = 82.8\%\)$ - For \(K = 50\): $\(\rho_{\text{dedup}}(50) = 1 - \frac{984\text{ GB}}{10,000\text{ GB}} = 1 - 0.0984 = 0.9016 = 90.16\%\)$

    Step 3: Asymptotic Efficiency $\(\lim_{K \to \infty} \rho_{\text{dedup}} = 1 - \delta = 1 - 0.08 = 0.920 = 92.0\%\)$ Conclusion: Under CAS, physical storage grows linearly at only \(16\text{ GB/week}\) instead of \(200\text{ GB/week}\). After 50 weeks, CAS saves over \(9\text{ TB}\) (\(90.16\%\)) of cloud storage.

    Self-Assessment 2: Content-Defined Chunking Boundary Re-synchronization Distance

    A \(5\text{ GB}\) binary matrix file is partitioned using Content-Defined Chunking with target average chunk size \(D = 64\text{ KB} = 65,536\text{ bytes}\) and sliding window \(w = 48\text{ bytes}\).

    A developer inserts a \(100\text{ byte}\) metadata header at offset 0 of the file.

    1. Explain why fixed-size chunking (\(64\text{ KB}\) fixed intervals) suffers \(0\%\) deduplication across the entire remaining \(5\text{ GB}\) file.
    2. Under Rabin Content-Defined Chunking, what is the probability that chunk boundaries re-synchronize within a distance of \(X = 3D = 192\text{ KB}\) from the insertion point?
    Reveal Detailed Solution

    Step 1: Fixed-Size Chunking Failure Analysis In fixed-size chunking, chunk boundaries occur at rigid byte offsets: \(0, 65536, 131072, \dots\).

    Inserting 100 bytes at byte 0 shifts every single subsequent byte in the file by +100 bytes: $\(\text{Chunk } 1 \to [100, 65635], \quad \text{Chunk } 2 \to [65636, 131171], \dots\)$ Because cryptographic hashes (SHA-256) exhibit the avalanche effect, shifting inputs by 100 bytes changes 100% of the chunk boundary contents. Consequently, every single chunk hash across the entire 5 GB file changes, resulting in \(0\%\) deduplication and re-uploading all 5 GB.

    Step 2: CDC Boundary Re-synchronization Probability (Definition 12.6.4) In Rabin CDC, cut boundaries are content-dependent, occurring whenever the rolling hash satisfies \(R_i \equiv 0 \pmod D\).

    Once the sliding window moves past the 100-byte insertion (at offset \(100 + w = 148\)), the byte sequence seen by the rolling window is identical to the original un-shifted file.

    At each byte position \(i \ge 148\), the probability of firing a boundary cut is \(p = \frac{1}{D}\). The probability of NOT firing a boundary cut in a span of \(k\) bytes is: $\(\Pr[\text{No cut in } k \text{ bytes}] = \left(1 - \frac{1}{D}\right)^k\)$ For \(k = 3D = 3 \times 65,536 = 196,608\text{ bytes}\), using the exponential approximation \((1 - 1/D)^D \approx e^{-1}\): $\(\Pr[\text{No cut in } 3D \text{ bytes}] \approx e^{-3} \approx 0.0498 = 4.98\%\)$

    Therefore, the probability that at least one boundary cut occurs (re-synchronizing the stream) within \(3D\) bytes is: $\(\Pr[\text{Re-sync within } 3D] = 1 - e^{-3} \approx 1 - 0.0498 = 0.9502 = 95.02\%\)$

    Conclusion: With over \(95\%\) probability, the stream re-aligns within \(192\text{ KB}\). Only the first chunk is modified; the remaining \(4.9998\text{ GB}\) (\(> 99.99\%\)) of chunks retain identical cryptographic hashes and are deduplicated with zero network transfer.
